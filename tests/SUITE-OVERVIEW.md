# zensu-claude-code — Full Test Suite Overview

Static inventory of every test suite in this repository: what exists, what each layer
covers, and how the layers are wired into CI.

Derived by reading `tests/run-all.sh`, `tests/profiles/promptfoo-local-only.v1.json`,
`tests/profiles/windows-ci.v1.json`, `.github/workflows/*.yml`, and each suite's own
source — not from an executed run. Assertion counts are approximations derived from
each suite's `check()` / `run()` / `expect()` call sites.

**The structure-suite counts are owned by `tests/profiles/promptfoo-local-only.v1.json` and the
unit-file facts by `tests/profiles/unit-files.v1.json`, not by this file.** Before any suite
runs, `run-all.sh` compares the manifest with the `tests/structure/test-*.sh` listing and the
registry with every `*.test.js` under `tests/` that git does not ignore, and it refuses every
mode when either disagrees. The totals in §1 and the table in §4 are generated from those two files by
`node tests/structure/lib-unit-registry.js render --write`, and `test-unit-registry.sh` fails
when either generated region differs from the renderer's output, so neither can go stale
silently.

**§3 is a hand audit.** At this commit every classified suite appears in exactly one §3 group,
and each group header equals the number of suites it lists, re-derived by comparing the group
lists with the manifest. Nothing machine-checks that: the next suite added without touching §3
breaks it again, so re-derive rather than trust it when the numbers matter. §7's profile table
was re-derived from `tests/profiles/windows-ci.v1.json` rather than described, so its nine
shard ids and their membership are the JSON's own, and the entry total is **44**.

**Windows coverage of `test-artifact-redaction.sh` is deliberately
STRUCTURAL-ONLY.** The suite is in `ciStructureTests`, so POSIX `run-all.sh --ci`
runs it, but it has no entry in `tests/profiles/windows-ci.v1.json` and therefore
never executes on a Windows shard. That is a decision, not an oversight: its
Windows wall clock is unmeasured, every shard is already budgeted against
`profileTimeoutMs`, and a suite receives the shard's REMAINING budget rather than
its own cap — so an unmeasured addition risks killing the tail of a shard rather
than adding coverage. Of the module's three Windows-only code paths, exactly one has a Windows pin:
`platformNoFollow`, in `test-windows-portability-guards.sh`, which IS in the
profile. The `\Users\<seg>` residual rule and the `msysSpelling` inverse are
driven only by the host-independent R11c inside this suite, so on Windows they are
exercised NOWHERE — stated plainly rather than left implied by a broader claim. Re-decide this if a Windows wall clock
is ever measured for the suite.

## 2. Run modes (`tests/run-all.sh`)

| Mode | Selects | API cost |
|---|---|---|
| *(no arg)* | every structure suite + the offline evals (counts in §1) | none |
| `--ci` | the CI structure suites (the Promptfoo local-only ones are skipped as `LOCAL`) + the offline evals with `ciArgs` (counts in §1) | none |
| `--self-check` | deterministic + the 7 live suites' skeleton mode | none |
| `--live` | deterministic + 7 live suites with fixture setup | **yes** |

Exit 0 only if `FAIL=0 && HANG=0 && BLOCKED=0`.

Runner-level guarantees (themselves pinned by `test-run-all-preflight-watchdog.sh` and
`test-run-all-required-offline-suites.sh`):

- **Preflight classification gate** — the manifest's `ciStructureTests` ∪
  `localStructureTests` must exactly equal the real directory listing, duplicate-free,
  and every `ciOfflineSuites` path must exist. Otherwise the run refuses to start.
  A new structure test that nobody classified fails the run rather than being skipped.
- **Preflight unit-file census** — every `*.test.js` under `tests/` that git does not ignore must
  have exactly one valid entry in `tests/profiles/unit-files.v1.json`, and each entry's
  `registered` must equal the file's column-0 `test(` registrations. A file is refused too when
  it has an indented `test(`; a `t.test(` that starts a line (optionally after `await`, `return`
  or `void`), where `t` is the one parameter a column-0 case declares in a callback head ending
  its own `test(` line; or a line-start `describe`, `it` or `suite` destructured from `node:test`
  by a `require` or `import` that starts its line. The static count cannot see such a case.
  Otherwise the run refuses to start and names each path; a case the census cannot see fails its
  driver's grade instead.
- **Per-suite watchdog** — `ZENSU_SUITE_TIMEOUT` (default 3600 s), portable pid poll
  (no GNU `timeout` on macOS). A suite that never returns is reported `HANG`, not `FAIL`.
- **Output to a file, never a command substitution** — so a suite leaving a background
  child alive cannot silently wedge the whole runner.
- **`BLOCK` state** — suites needing npm devDependencies (`node_modules` absent) are
  reported as *blocked, not run*, and still fail the overall result. No silent skip.
  The manifest declares which suites these are: `needsNodeDeps` on each `ciOfflineSuites`
  entry, and the `nodeDepsStructureTests` list for structure suites. Every entry of that
  list must also be in `ciStructureTests` or `localStructureTests`, without duplicates,
  or the run refuses to start. Membership is pinned too: the watchdog suite fails while a
  structure suite, CI or local, is missing from that list although its own source, a unit
  file it drives, or a local module such a unit requires needs a `package.json` package —
  through `require` or `import`, a `node_modules/.bin` binary, `npx` / `npm exec`, or
  `npm run` of one of its scripts.
- **Offline inventory count check** — executed suite count must equal the manifest count.

`hook-payload-stdin` is the one suite in this group that reads EVERY hook. It drives
`tests/structure/hook-payload-stdin-scan.js` over `hooks/*.sh` and `hooks/lib/*.sh` and fails
when a hook hands its payload to a child process through an environment prefix, an `export` or
`declare -x`, or an argument. An environment string over the exec limit (131072 bytes per string
on Linux, 1048576 bytes for argv plus environment on macOS) makes the exec fail with E2BIG, the
child prints nothing, and a hook that reads the empty output as nothing to do fails open; that is
how the CLI gate and the TDD phase gate once let oversized payloads through. The scanner lexes
the shell itself (quotes, heredocs, `case` patterns, `[[ ]]`, command substitutions) and follows
the payload from the `INPUT` name and from every whole-stdin read (`$(cat)`, `$(head …)`,
`$(dd …)`, `read -d ''` outside a loop condition) through plain and `local` copies into the
positional parameters of each function it reaches, resolved in the calling file first and then in
`hooks/lib/`. A builtin or a known function may take the payload as an argument; every other
command must get it over stdin, which is the remedy the failure names. A file the scanner cannot
parse fails the check. The controls flag nine leak shapes, leave the safe shapes unflagged, and
prove that the scan read every file and found the payload read in every hook script that reads
stdin. The coupling runs in the unobvious direction, as for `bash32-portability`: an ordinary
edit to any hook can turn this suite red, and the remedy is in the hook that changed. It does not
follow a payload through `eval`, `source` or `set --` arguments, an indirect `${!name}`, or a
variable other than `INPUT` that one file assigns and another reads; it does not read code held in
a quoted string, such as a `trap` handler; and it does not track values derived from the payload,
such as the prompt or command text a hook extracts. It is not in
`windows-ci.v1.json`: it reads files and runs no hook, so it has no Windows dimension.

`test-bash32-portability.sh` is the odd one out here: its platform is macOS, not
Windows. It is grouped with these because it guards the same KIND of defect — a
host shell that reads a source file differently from the one the author had. macOS
ships GNU bash 3.2.57 as `/bin/bash`, and that release extracts a `$( ... )` body
with a naive paren scanner, so a `case` arm in the bare `pattern)` form closes the
substitution at its own `)`. The suite drives
`tests/structure/bash32-substitution-scan.js` over every `*.sh` in the tree and
takes bash's own verdict on the body the naive scanner would have handed the
parser, so it reports identically on a 3.2 host and on a 5.x runner. It is NOT in
`windows-ci.v1.json`, deliberately: every shard there is already close to its
`profileTimeoutMs`, and the check has no Windows dimension to justify paying for
one. The coupling runs in the UNOBVIOUS direction that CLAUDE.md records for G12 —
an ordinary edit to any shell file in the tree can turn this suite red, and the
remedy is in the file that changed.

Git-Bash/MSYS path translation boundaries, native-Node module loading from a plugin
root containing whitespace and an apostrophe, the Windows CI manifest contract, and — in
`test-windows-portability-guards.sh` — the per-file secure-open inventory plus the
marker-block-carrier contract that binds the two rule-injecting hooks to one reader, one `MAX_FILE` and one
`MAX_BLOCK`. Those three read the two hook files and sit directly beneath the per-file

Every driver runs its files through `tests/structure/lib-unit-registry.sh`. `unit_run` runs one
file under the TAP reporter and grades that run against the file's entry: node's exact
registered total, the per-host ceiling of skipped or todo cases (`darwin`, `linux`, `root` for
uid 0, `win32`), and the guarded titles that must pass. An emptied file fails even at
`registered: 1`, because node then counts the file itself as its only test. `unit_grade` grades
a run a driver spawned itself, which `tests/session-control/run.sh` does to keep its timeout and
progress diagnostic, and `unit_registry_done` fails a driver that never ran a file the registry
gives it on this host. A host an entry's `notRunOn` names owes no grade and refuses one; a
driver that leaves such a host early calls its done check first, so it passes there only while
the registry declares the exclusion. A failing grade replays each `not ok` line on stderr with
its YAML block and the last 40 diagnostic lines node printed since the case before it, counting
any earlier ones it leaves out, or the last 40 lines of node's output when no case reported
`not ok`. A new unit file needs its entry, with skip counts measured on each host that runs it,
in the same commit, followed by `node tests/structure/lib-unit-registry.js render --write`.

## 9. Known gaps and caveats

- The shifted-clock pass in `scheduled.yml` moves `Date` in node processes only, and only
  for `tests/structure/*.test.js`: the shell suites, `tests/session-control/`, child
  processes that are not node (`git`, `date`), file mtimes and any node child whose
  environment drops `NODE_OPTIONS` or `ZENSU_TEST_CLOCK_SHIFT_DAYS` stay on the real clock.
  A test that compares a file mtime, a git date or a lease age with `Date.now()` therefore
  fails under the shift unless it moves both sides onto one clock, as `tests/README.md`
  describes; the allowlist names each test that cannot, with its dependency
  (`file-mtime`, `git-date` or `lease-staleness`).
- 5 eval directories are not wired into any `run-all.sh` mode
  (`verify-feature`, `context-nudge-reaction`, `zen-mode-reaction`, `plan-approval-hook`,
  `route-short-line-reaction`).
- The 2 offline eval self-checks whose `ciOfflineSuites` entry sets `needsNodeDeps`
  (`session-control`, `reset-review-limit`) and every structure suite listed in the
  manifest's `nodeDepsStructureTests` need `npm ci`; without `node_modules` they report
  `BLOCK` and the run is not green. The manifest owns that structure-suite list, so it is
  not copied here.
- The promptfoo/expect harnesses under `evals/tdd-manager/`, `evals/tdd-manager-pretool/`,
  and `evals/tdd-review-chain/` still target the pre-0.4.0 `zensu:tdd-manager` subagent
  that was removed when TDD moved to the main thread. Rewriting them to the main-thread
  `/zensu:build` model is pending (also noted in `tests/README.md`).

## 10. Maintaining this document

A new structure suite must be classified in `tests/profiles/promptfoo-local-only.v1.json`, and
a new `node --test` file needs its entry in `tests/profiles/unit-files.v1.json`; the run-all
preflight refuses every mode otherwise, and those gates, not this file, are the enforcement
points. §1's totals and §4's table are generated: edit the two JSON files and run
`node tests/structure/lib-unit-registry.js render --write`, never the regions by hand.
`test-unit-registry.sh` fails when a region differs from the renderer's output. The rest of
this overview is descriptive, and §3's group lists are updated by hand when suites are added
or removed.

## Suite-prologue re-entry guard (cross-suite convention)

`test-evidence-discipline.sh`,
`test-best-solution-first.sh` and `test-windows-portability-guards.sh` each set
`ZENSU_SUITE_PROLOGUE_ENTERED` and refuse a second pass through their own prologue. A suite
file containing a spliced copy of itself otherwise resets `PASS`/`FAIL` and reports a
plausible total; that happened for real. It is a three-way hand copy in the three suites this
convention started in — every other `tests/structure/test-*.sh` is still unguarded. Adopting
it corpus-wide is an open item; at a fourth adopter, hoist the block into a sourced helper
instead of taking another copy.
