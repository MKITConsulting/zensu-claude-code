# Verdict mechanics and gotchas

Read this when you explain a `TAKEOVER` verdict, a queue note or a withdrawn prompt, or when a session's age, branch or worktree looks wrong.

## Verified gotchas

- **A live session that ended its turn is waiting for its human, not working — the file mtime cannot tell those apart.** Freshness and activity are different things, so a session whose transcript ends on an `assistant` record with `end_turn` or `stop_sequence` reads `PROBABLY_FREE` even inside the 15-minute window. Two deliberate exceptions stay `BUSY`: anything under **2 minutes** old, where the turn may still be streaming, and an assistant record whose stop reason is null, absent, or outside the accepted token shape — uncertainty resolves towards "still working", which costs one question rather than a wrong takeover. A sidechain record counts as in-flight too: a subagent is running. An **API-error record is skipped**, so a session that died on a rate limit is not reported as mid-turn — that is precisely the session flow 5 exists to take over.
- **A session's activity — every age, freshness window and recency order this skill reports for it — is measured from its turn records rather than from the file's modification time, which only caps a turn timestamp and stands in when none can be read.** The desktop app and the harness keep appending records that are not turns — `custom-title`, `agent-name`, `last-prompt`, `mode`, hook bookkeeping — long after a session's last turn, so a title update must not flip an idle session to `BUSY`. So the 2-minute and 15-minute windows and the `silent for` and `wrote … min ago` ages read the newest turn record — an API-error record counts there, since it is a turn the process attempted — and the `ended its last turn (…) … ago` age reads the timestamp of the record that ended it. A turn timestamp later than the file's own write is taken as that write, and with no readable turn timestamp the write time is the fallback, which can only make a session look fresher. `show`'s `LAST` row, both briefs' `last activity` line, the takeover brief's plan-document window, the `--days` scan window, the age and order of `list` and `limited`, and the selector collapse onto one session's newest transcript or one directory's newest session read the same record; the file's write time only pre-filters the `--days` window. `show` appends `(file last written … ago)`, the file's own write time, when that is at least a minute later. `--json` carries both timestamps, uncapped and converted to standard ISO form, as `lastTurn.at` and `lastTurn.activityAt`, and as `lastActivity` the newest turn record's time after that cap and fallback — the time every reader above uses except the `ended its last turn` age, which reads `lastTurn.at` under the same cap. Two clocks stay apart on purpose: the queue's 15-minute staleness reads the `enqueue` record's own stamp (below), and `lineage --backfill` still picks a successor by the file's write time. One residual: a Stop hook that blocks writes an attachment rather than a turn record, so until the continuation's first record lands the session reads as having ended its turn. A second residual is the price of the rule itself: a tool call writes its result record only when it returns, so a live session blocked on one reads `PROBABLY_FREE` once the call passes 15 minutes, and its reason line then names a turn in flight. Long waits are mostly `AskUserQuestion` prompts and `ExitPlanMode` approvals, which wait for the user, but an `Agent` or `Bash` call can return and act on its own.
- **On a transcript past the 8 MB full-read limit, the last turn is read from the tail segment only.** Finding nothing in the tail yields "no last record could be read", which routes to `BUSY` inside the 15-minute window with a reason that says exactly that, rather than naming a turn nobody observed.
- **A queue depth is a balance, not a count — except inside the tail window, where it is a lower bound.** Every `enqueue` adds one, and every record that takes a prompt back out subtracts one: `dequeue` (the prompt became a turn), `remove` (it left without one — the user deleted it, the running turn absorbed it, or an agent received it), and `popAll`/`popOne` (pulled back into the input box, one record per prompt). A record that takes a prompt out while the depth is already zero is clamped at zero and counted as an overdraw (`overdrawn`, `overdrawnAt` in the `queue` field of `--json`), because it shows the balance missed a record — an `enqueue` in another file, or a second consumer for one prompt. On a full read one younger than 15 minutes makes a `PROBABLY_FREE` reason say the queue could not be measured, under the same stamp rules as an unknown record two bullets below; a tail-window scan does not count one, because a consumer there legitimately answers a prompt enqueued in the unread middle. A reliable depth whose last `enqueue` is older than 15 minutes is treated as stale, and that rule also bounds the two things counting cannot close, two bullets below — except that a stamp it cannot read never ages under it, and one ahead of the clock does not age until the clock reaches it. Every suppressed case is named in a `PROBABLY_FREE` verdict's reason rather than silently dropped; a `BUSY` or `FREE` reason carries no queue note, because `BUSY` already forces the go/no-go and `FREE` means no live process or an app-archived session.
- **Inside the tail window the depth is a lower bound, and only a positive one is evidence.** On a partial read the depth is counted over the **tail slice only**: an `enqueue` inside that slice that no consumer follows is genuinely pending, because everything after it was read. A consumer that names a prompt the slice never enqueued is treated as belonging to the unread middle and skipped, so it cannot cancel a prompt that is still waiting — a `remove` whose content no longer matches its `enqueue` is skipped the same way, which can only over-report a prompt, never hide one. A consumer that names nothing — every `dequeue`, and the few `remove` records without content — still counts, so one inside the slice that in fact took a prompt enqueued in the unread middle drives the slice depth to zero beside a prompt that is genuinely waiting; that zero is reported as unmeasured and costs the go/no-go, never a silent takeover. So a positive tail-slice depth **does** count as evidence; a zero one does not, and neither does a depth spanning the unread gap.
- **Two things counting cannot close, and both are named in the reason.** A prompt can leave with no record at all — the process exits, or Claude Code resets its queue — and no later record clears that phantom; only the 15-minute staleness rule bounds it, and an `enqueue` whose stamp cannot be read never ages under that rule, while one ahead of the clock does not age until the clock reaches it, so such a phantom reads `BUSY` until a later record moves it on — a consumer that empties the balance, or an `enqueue` carrying a readable time — the process ends, or the desktop app archives the session; over-reporting, never hiding. And a queue record of a kind this script does not know leaves the depth alone, because it may add a prompt as easily as take one out: when such a record is younger than 15 minutes — or carries a stamp that cannot be read, which never ages, or one ahead of the clock, which does not age until the clock reaches it — a `PROBABLY_FREE` reason says the queue could not be measured, beside a depth of 0 instead of claiming that nothing is queued, and beside a stale depth instead of calling it not a waiting prompt; `BUSY` and `FREE` reasons carry no such clause. A stamp ahead of the clock counts as fresh and is worded as such rather than rendered as "0m ago".
- **The prompt listing sets a queued prompt apart as withdrawn only when it can see no delivery of the same text.** It is a separate reader from the depth and answers a different question — what the session was asked — and every place that lists a session's prompt history reads it: `show`'s prompt timeline, the `prompts` field of `show --json` and `takeover --json`, the takeover brief's original objective and recent instructions, and the handoff brief's list of what was asked. A withdrawn prompt is not dropped: `show` and both briefs print it in a separate section headed as withdrawn before sending, with the instruction not to act on it, and `show --json` and `takeover --json` carry it as `withdrawnPrompts`; a text also listed as sent appears only among the sent. The one-line label that `list`, `limited` and an ambiguous selector show beside a session is not one of them: it is the session's title when it has one, otherwise the harness's own `last-prompt` record, and this rule filters neither. A `popAll` or `popOne` withdraws the copy it pulled back into the input box, but only in a full read: in a truncated one the per-name match can take a copy from the part that was read whose own consumer sat in the unread middle, so a truncated read withdraws nothing of either kind — `show`'s truncation note and both briefs' say so, and under `--json` `truncated: true` means the same for the `prompts` field, while `withdrawnPrompts` is `null` rather than empty, because no withdrawal was judged. A `remove` alone proves nothing, because Claude Code writes one for a delivery as well, so a `remove` with no `reason` withdraws its copy only when no `queued_command` attachment — the harness handing a queued prompt to the model — is credited to it. Only a `remove` that took a copy and carries no `reason` can be credited, and the pairs of one text are credited nearest pair first, each attachment and each `remove` at most once, within `QUEUE_DELIVERY_REACH` (100) records before or after — so an attachment can end up credited to a farther `remove` or to none, and a prompt withdrawn and then sent again is listed at the time it was delivered. Three more conditions must hold before it withdraws, and each one errs toward listing a withdrawn prompt. The read must be full, because a truncated one can hold the delivering attachment in its unread middle. At least 100 records must follow the `remove`, because a live read can land before its attachment is written. And the build that wrote it must have opened its delivery channel without vetoing it. A build is the `version` of the last record before the `remove` that names one — a user record that is not a tool result or a sidechain record, or an attachment whose line carries a `queued_command` type or a `prompt` field — and a `remove` followed by a record of another build is judged under both. A build opens with a `queued_command` attachment whose prompt text is readable, and is vetoed by one whose `prompt` is neither a string nor an array, by one whose text matches no enqueued copy, or by an attachment of another type whose `prompt` carries an enqueued text: a build that fails that test may have changed how it hands a prompt over. A `remove` carrying a `reason`, a content-less `remove` and a content-less pull-back withdraw nothing, and a text that any readable `queued_command` attachment carries keeps at least one copy listed. The rest is a residual the listing cannot see: a delivered prompt is still set apart as withdrawn when its delivery was never written; a readable delivery that sat more than `QUEUE_DELIVERY_REACH` records from every `remove` of its text still keeps its text listed, though it may be listed at another copy's time when the text was queued more than once; and a delivery whose text changed on the way vetoes its build instead, unless the changed text happens to match another enqueued copy.
- The project-dir slug is `cwd.replace(/[^A-Za-z0-9]/g,'-')`, but **the directory name does not always match** the `cwd` inside a transcript's own records. Never resolve a session by directory name — the script reads `cwd` out of the records for exactly this reason.
- A transcript's `gitBranch` can flicker to `HEAD` for a single record during a detached moment. Never take the last value blindly — the script takes the last value that is neither empty nor `HEAD`, and prefers the worktree's live branch when resolving file names.
- A worktree gets **reused**: the session you are taking over may have run on a branch the worktree no longer has checked out. Compare the session's recorded branch against the live one before assuming the working tree still holds that work. Brief filenames are keyed to the **session's own** branch, not the worktree's current one.
- A session's `cwd` is taken from its **first** record; later records can point at a subdirectory the session `cd`-ed into. The script reports the worktree root separately (`WORKTREE` vs `CWD`).
- Expect many more live registry entries than open windows. Treat each entry as one session process, not one window.
- The registry carries **no account or login field** (`pid, sessionId, cwd, startedAt, procStart, version, peerProtocol, kind, entrypoint, name, nameSource`). So it cannot prove which login owns a session — report the pid and cwd, never assert an account.
- `status`, `statusUpdatedAt`, `updatedAt` and `messagingSocketPath` appear on **some** entries only, and only for certain entrypoints. Do not build a liveness or busy/idle check on them; `kill -0 <pid>` is the signal that works everywhere.
- Transcripts over 8 MB are read head+tail only; `show` prints a `NOTE` when the middle was skipped, so a sparse prompt timeline on a big session is expected, not a bug.
- `STATUS GONE` means the worktree directory was deleted. The branch usually still exists — `git worktree add <path> <branch>` brings it back.
- **The runnable `cd -- <cwd> && claude --resume <id>` lines are built from untrusted values, and are shell-quoted rather than trusted.** The `cwd` is read out of another session's transcript and the session id is the transcript's **filename** with `.jsonl` stripped, never validated as a session id. There are five such lines: the two `show` prints, the handoff brief's `## Continue this work` fence, the takeover brief's `## How to continue` step 1 (a bare `cd` to the **worktree root** with no session id), and the one the `CONTINUE not needed` branch renders, which IS the full form. Every operand in all five is POSIX single-quoted with line breaks collapsed, which makes `$( )`, `;`, `&&` and `|` inert. **One residual gap:** the `--` guards the `cd` operand only, so a session id spelled like an option is not neutralized for `claude --resume`. Read a line before running it.
