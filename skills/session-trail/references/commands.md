# session-trail commands, flags and selectors

Read this before you pass a flag, resolve a selector, read `--json`, or run `--force`,
`lineage --forget`, `label` or `release`. The one-line table in `SKILL.md` names every
command; the details are here.

## Command details

| Command | Details |
|---|---|
| `instances` | every live session on the machine, grouped by repo. It reads the registry directly, touches no transcript and no git, and is always fast. |
| `list` | sessions for the **current** repo (all its worktrees), live and finished, with git + PR state. The slow path at the default window: use `--days 3` or `--no-git` when you only need to locate something. |
| `show <selector>` | deep digest of one session: prompt timeline, last assistant output, git state, touched files, resume commands, the `TAKEOVER` verdict and the `WRITES` line. |
| `handoff <selector>` | emits a handoff-brief markdown skeleton to stdout, plus the target path to write it to. Writes nothing itself. |
| `limited` | sessions that hit an API limit or error, split into **STALLED** (the error is the last thing in the transcript) and **RECOVERED** (turns followed it), with the cause and usually the reset time. Only the stalled ones need a takeover. |
| `takeover <selector>` | full continuation brief: objective, last compaction summary, reconstructed task list with status, recent instructions verbatim, the final assistant turns, plan documents on disk, git state **including the actual uncommitted diff**, touched files. **Also records the handover as a lineage edge** unless `--no-record` is passed, see below. |
| `lineage` | the recorded handover chains for this repo (`--all` = machine-wide): each link with its session, account, worktree/branch and live status. |
| `lineage --where <session-id or id prefix>` | where is this session being continued now. Takes a session id or a prefix of at least 6 characters, NOT the `<selector>` below; a worktree name or PR number does not resolve here. |
| `lineage --diagnose` | which desktop-store path was found, which were probed, the config root, the ledger path, the edge count. |
| `lineage --backfill [--apply]` | reconstruct handovers from before the ledger existed. **Scans UNBOUNDED unless `--days` is passed explicitly.** Dry run without `--apply`; written edges are marked `inferred`. |
| `lineage --forget <session> [--apply]` | remove every record naming that session on either endpoint. Dry run without `--apply`, which lists the files it would take; the removal is machine-wide and cannot be undone. An ambiguous prefix is refused, and an unreadable ledger refuses rather than reporting nothing to remove. |
| `adopt <selector>` | record a handover explicitly, when `takeover` was not the route. It also prints the **same destination guidance the briefs carry**: the own-worktree rule from flow 3 step 4 and, while the source directory is readable, the carry-over recipe, because a `git worktree add` moves only what was committed. `--json` exposes it under `worktreeAdvice`, as `show` and `takeover` do. The receipt slot carries either `RECORDED ` or `NOT RECORDED `, and the second CONTAINS the first, so a consumer matching the success token must anchor it at the start of the line. |
| `release <selector>` | lift this plugin's `.worktree-keep` protection from a session whose work moved to you, the closing step of every takeover, so Claude Desktop can archive or remove it and clean its worktree up. Dry run without `--apply`. It refuses, naming each reason: while you or another live session works inside that worktree; while that session is `BUSY`, or registered with a queue it could not measure (re-run with `--force`, as on `takeover`: the user's request to release, or the takeover they confirmed, is the go); while the session registry cannot be read completely; while a nested repository other than a submodule is inside, or the scan for one did not finish; and while a keep anchor it cannot attribute, cannot validate, or that was recorded for another worktree path holds the marker. With `--apply` it ends that session's keep anchor, and the anchor of any known session that is no longer running, through the worktree-keep module; it never archives, deletes or moves anything itself. Once nothing holds the old session it prints an `ARCHIVE` line saying the old session can now be archived or removed, and where, and reporting uncommitted, unpushed and ignored files still in the old worktree, which an archive deletes. Relay all of it to the user. The receipt words are `READY`, `RELEASABLE`, `RELEASED` and `BLOCKED`, and none contains another; a `BLOCKED` run with `--apply` exits 1. |
| `label <accountUuid\|appPid\|--self> <text>` | give an account (or a window) a readable name. An account UUID is stable; a window label is keyed by the process incarnation (pid plus start time), so a pid that exits takes its label out of every rendering, and labelling a pid with no running process is refused. |
| `label --remove <accountUuid\|appPid>` | clear a label. A window removal takes every incarnation recorded under that pid. Removing a key that is not there says so. |
| `window-probe` | **test seam, not for use.** Reads `{ pid, table }` on stdin and returns the window pid the ancestry rule selects. Reads nothing from the machine and writes nothing. |

## Flags

`--all` (every repo, not just this one) · `--repo <path>` · `--days N` (default 21, `0` = unbounded) · `--prompts N` (default 12) · `--live` (live only) · `--no-git` (skip git calls, much faster — honoured by `list`, `show` and `release` only; `release` then cannot report the old worktree's uncommitted, unpushed or ignored files; `takeover` and `handoff` run their git calls regardless) · `--json` (honoured by every command except `handoff`, which always emits markdown) · `--force` · `--config-dir <path>` · `--no-record` · `--reason <text>` · `--where <session-id>` · `--diagnose` · `--backfill` · `--apply` · `--self` · `--forget <session>` (at least 6 characters, like `--where`) · `--remove <key>` · `--anchor <path>` (your own project root, for the `CONTINUE` verdict — `show` and `takeover --json` only; see `references/takeover.md`).

**Every operand-taking flag is validated, and a missing or malformed operand is refused.** `--days` and `--prompts` take a number: `--days --all` exits 1 with `session-trail: --days needs a number (got "--all")` rather than falling back to an unbounded scan. `--config-dir`, `--where`, `--reason`, `--repo`, `--anchor`, `--forget` and `--remove` refuse a value that is empty or itself starts with `--`. Always write the value explicitly: `--days 3`. `0` is the deliberate spelling for an unbounded window, and `list` prints `WINDOW unbounded` in its header then; under `--json` there is no header, so check the `--days` value you actually passed.

**A flag is also refused by any command it does not belong to.** The dispatcher checks the supplied flags against the invoked command before the handler runs. The one documented exception is `--force` on `list` and `limited`, below.

## The ledger write and its confidence tiers

**`takeover` writes one lineage edge, and says so on its own line.** Every other read command writes nothing; this one does, because an unrecorded takeover is indistinguishable from one that never happened. Both the text and the `--json` path record it (`lineage.recorded` in the payload). `--no-record` keeps a run read-only: the takeover flow builds its plan with it and records only after the user confirms, with `takeover --force`. Nothing is recorded when the target is this same session, or when the process has no `CLAUDE_CODE_SESSION_ID` and therefore cannot name the continuing session; in both cases the reason is stated.

**Every edge carries a confidence tier, and it is ordered: `confirmed` > `provisional` > `inferred`.** `adopt` and `takeover --force` write `confirmed`; a plain `takeover` writes `provisional`, because generating a brief is not the same event as having taken the session over; `lineage --backfill` writes `inferred`. The order GATES rather than decorates: for the same pair of sessions a guess never displaces a measurement, and the chain walk prefers a measured successor over a newer guessed one. Any tier below `confirmed` is annotated in every rendering.

**A `--backfill` edge is a GUESS and is rendered as one.** The heuristic: a session that stalled on an API limit, and the next session on the same worktree under a *different* account. A successor under the same account is a resumption, not a handover, and is never proposed; two sessions whose account could not be resolved are not evidence of a different one either.

**Selectors are repo-scoped, so `adopt` and `takeover` usually need `--all`.** A session in another repo does not match without it.

**The script's ONLY write channel of its own is the lineage ledger, and `release --apply` is the one verb that changes anything outside it — through the worktree-keep module, never by a write in this script.** It creates `<config root>/zensu/session-lineage/v1/` and writes edge records and `labels.json` there, and nothing else: no transcript, no registry file, no handoff brief, no git mutation, and exactly one delete channel — `lineage --forget <session> --apply`, which unlinks edge records inside the ledger directory and nothing else. Apart from that, no delete or rename outside its own two temp families there, `.edge-*.tmp` and `.labels-*.tmp`: both write their temp first and remove it on failure. An edge record lands with `link`, which refuses a name that already exists, while `labels.json` lands with `rename`, which replaces the whole document; that difference is the append-only guarantee. The handoff and takeover briefs are printed to stdout for you to write with the Write tool, so that write stays visible to the user. `release --apply` hands the keep anchors in the released session's worktree to `retireAnchors` in `hooks/lib/worktree-keep-v1.js`, which records an end time on each and lets `reconcileKeep` remove the `.worktree-keep` marker once no live or unreadable anchor holds it. It ends only anchors whose session is the released one or is no longer running, and changes nothing else there; its `git status` runs with `--no-optional-locks`.

## `--force`

**`--force` writes nothing and forces nothing on disk.** It re-renders a `BUSY` verdict as `CONTESTED`, keeps the measured fact verbatim in the reason, and never changes a `FREE` or `PROBABLY_FREE` verdict — though under a `PROBABLY_FREE` whose reason says the queue could not be measured, `show` then prints the proceed advice instead of the unmeasured-queue advice, because the flag is the recorded answer to the plan confirmation, carried under `--json` as `takeover.authorized: true`. The flag adds no write of its own; on `takeover` without `--no-record` it marks the edge that verb records anyway as `confirmed` rather than `provisional`. Its only purpose is to put the user's approval of a takeover — or, on `release`, of lifting a busy session's keep protection — on the command line, where it is visible to them and to the next reader.

The measurement and the approval stay **separate fields** under `--json`: `takeover.measuredLevel`, `takeover.measuredReason` and `takeover.queueMeasured` are what was observed and never change, `takeover.authorized` says only that the flag was passed, and `takeover.level` is what to act on. Report `takeover.measuredLevel` and `takeover.measuredReason` when you state the hazard: `authorized` records a caller's claim, not an observation.

**`--force` is ignored by the two selector-less commands that carry a verdict, `list` and `limited`, on every carrier.** (`instances` is selector-less too, but emits no verdict, so it **refuses** the flag instead.) One session's approval is not approval for every busy row on the machine, so their rows always report the measurement and `authorized` is always `false` there. The rule lives at the verdict boundary (`surveyVerdict`), not in a renderer.

## Unreadable records and counts

**A record that cannot be read is skipped, not fatal.** An unreadable transcript, registry file, desktop record or plan directory does not abort the command. A title, a last prompt or a timestamp that is not a string inside a record that does parse is read as absent. Every command prints a `NOTE n record(s) unreadable and skipped` line in plain-text mode; under `--json` the count travels in the `skipped` field instead, on every command that emits a payload. `handoff` ignores `--json` and keeps the plain-text NOTE. A failed selector lookup names the count too. When the count is non-zero, say so: the answer is incomplete.

**Always state the window with any count you report** (except `lineage --backfill`, which prints its own `WINDOW` line). `--days` defaults to 21, so "4 stalled sessions" silently means "4 in the last 21 days". Say which window you scanned, or scan `--days 0` when the user asks a machine-wide question. Same for `--all`: without it, counts cover the current repo only.

## Selectors

`<selector>` is resolved in this order: full session id → id prefix (≥6 chars) → PR number (`772` or `#772`) → exact worktree name or path → exact branch → partial worktree/branch → text in title or last prompt, where a session whose title equals the selector (compared case-insensitively and trimmed) in any of its transcripts outranks every other session the text tier matched. **Your own session is never picked by the last five.** `CLAUDE_CODE_SESSION_ID` names it, and only its full id or an id prefix selects it: the desktop app titles a new session after its first prompt, and that prompt usually quotes the very selector being resolved. When it matched and was skipped, a `NOTE` line names it, says this is your own session and says what works instead — `show` and `handoff` select it by its session id, `takeover` points at `handoff`, and `adopt` says a session never adopts itself. Under `--json` that line goes to stderr, and the `show`, `takeover` and `adopt` payloads carry the skipped id as `selfSkipped` (null when nothing was skipped). A lookup that only it matched fails with exit 2, and a session selected by its id is labelled `(this is your own session)` in `show` and in a candidate list. Several matches collapse to the one with the newest turn record only where they are one line of work: on the two id tiers and the text tier when every match is the same session id, and on the PR, worktree and branch tiers when every match is the same session id or they share one recorded working directory. Two different sessions an id prefix matches are always reported, and so are two different sessions the text tier still holds after the exact-title rank. On an ambiguous match it prints the candidates and exits 2 — re-run with a sharper selector.

## Printed follow-up commands

The follow-up commands the script prints (`next: node <path> show ...`) embed the resolved script path, which on an installed plugin is a version-pinned, percent-encoded cache directory that changes on the next update. Give the user the `${CLAUDE_PLUGIN_ROOT}` form from `SKILL.md` instead.
