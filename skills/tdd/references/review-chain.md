# Phase 6 step 10: close implementation and run the review chain

Read this at Phase 6 step 10, after steps 1 to 9 in `references/audit.md`, and again at the start of every review round the post-review directive routes back to you.

10. **Close implementation and trigger the review chain.** This replaces the old subagent auto-review hook — the chain is now driven from this main thread. Execute these steps STRICTLY ONE AT A TIME (single tool call per step, wait for each result; every Agent spawn sets `run_in_background: false`), never as a parallel batch beyond the review fan-out of step 3 and the judge pair of step 4b, and never bundled with the Phase 6 audit writes above:
    1. Mark implementation complete. **This verb REFUSES on two preconditions: the step 5b edit-landing receipt RECORDING A CLEAN AUDIT, and a usable `## Requirements` table in this session's plan** — run the audit first and fill the table, or completion fails closed, naming the command in both cases. A receipt is not a token: only `clean: true` under a known schema is accepted, so an audit that reported `EDIT NOT LANDED` or `PENDING PREDICATE` must be ANSWERED per step 5b c) — land the edit, or prove a pending claim with a current predicate — and re-run; a withdrawn claim is recorded but never clears the verdict, and a bare re-run over the same claims only regenerates the same refusal. The receipt requirement is armed by a changed tree OR by a logged claim, so a chain whose work landed somewhere the anchor cannot see is gated exactly like a dirty one. Pass `--plan {plan_file}` — the cwd-independent spelling defined in Principle 3 — so the table is judged against the plan you actually wrote; without the flag the gate derives it from the receipt's run log, which is the same stem. The flag is bounded: it must name a plan inside `{project_root}/.zensu/plans/` whose stem matches the run log this session's edit-landing receipt records, so it cannot silently pick up an unrelated plan. The bound is as strong as that receipt, not stronger — the receipt is an ordinary file in the project tree, so this is anchoring, not enforcement. For a standalone chain run `CLAUDE_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --tdd-complete --plan {plan_file}`. For a delegated Autopilot chain run the exact bound form `CLAUDE_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --tdd-complete --plan {plan_file} --autopilot-run "$RUN_ID" --autopilot-attempt "$ATTEMPT" --chain-id "$CHAIN_ID"`, using the immutable values accepted by this generation's bound begin. This arms the Stop-hook backstop (`stop-chain-enforcer.sh`): you cannot end your turn until the chain terminates or its Stop cap is hit. A non-zero bound completion that is NOT a precondition refusal is stale or mismatched: stop without spawning a reviewer or changing the current generation. **Classify by SHAPE, never by a closed pair of literals** — the refusals grew and a literal list goes stale silently: a receipt that records `clean: false`, one that carries no verdict, one that is unreadable or unparseable, and one that describes a DIFFERENT run log all name the receipt without carrying the words `no edit-landing receipt`. Every refusal whose text names the edit-landing receipt or the plan's `## Requirements` table is a precondition refusal, meant to be fixed and retried; only a refusal naming neither is stale or mismatched.
    2. Enumerate changed files and summarize the relevant changed hunks in this main thread. Take the file list from the canonical change set, `node "{plugin_root}/hooks/lib/review-packet-v1.js" changes --root "{project_root}" --baseline "$BASELINE_SHA"` (an empty baseline is accepted): its `changed_files` holds the tracked changes against HEAD, the commits since the baseline, every untracked non-ignored file and, on an unborn HEAD, every cached file, and `kind: explicit-no-git` means the root is outside git, so list the files your claims name. Never re-spell a subset of it with ad-hoc `git` listings. Read the hunks with `TOP="$(git -C "{project_root}" rev-parse --show-toplevel)"` and the guard `[ -n "$TOP" ] && [ -d "$TOP" ]` before any `git -C "$TOP"`: the corresponding `git -C "$TOP" -c core.quotePath=false --literal-pathspecs diff HEAD -- "<file>"` reads (a pathspec resolves against the cwd and is wildmatched unless literal, so an unanchored or non-literal read returns nothing for a nested project dir or a bracketed filename), a `git -C "$TOP" --literal-pathspecs diff "$BASELINE_SHA" -- "<file>"` read for a file that changed only in the mid-run-commit range, and a plain `Read` of `"$TOP/<file>"` for each new untracked file and, on an unborn HEAD, for every listed file (`git diff` shows nothing for those). A new file omitted here is invisible to every reviewer, which is the same blindness 5b exists to catch.
    2b. **Persona discovery (repo-local).** Pipe the step-2 list into `node "{plugin_root}/hooks/lib/persona-activation.js" "$TOP/.claude/agents"` — it decides which `.claude/agents/zensu-review-*.md` personas join (activation globs vs changed paths; no `activation:` field = always joins; cap 5, matched-before-always-join, each lexicographic). Append every `skip`/`drop` verdict to the run log humanized: `PERSONA SKIPPED — <name> (no activation match | malformed)` / `PERSONA DROPPED — <name> (over cap)` — no silent omission.
    2c. **Create the round's canonical `REVIEW PACKET v1`.** With the Write tool, write `{project_root}/.zensu/reviews/packet-input-round-<n>.json`, where `<n>` counts this chain's reviews from 1, as one JSON object of seven strings: `implementation_summary`, `requirements_baseline` (the plan's stable requirement IDs, or `none`), `diff_summary`, `test_evidence` (the runner's summary line of each Phase 6 run, verbatim, plus the scoped CHECKPOINT lines and the step 6d `ACCEPTANCE STATUS` lines), `build_evidence`, `coverage_evidence`, and `edit_landing_evidence` (the step 5b close marker plus any `EDIT NOT LANDED` lines — without it the panel and the judge cannot see that a step claiming a requirement produced no change); a project outside git adds `changed_files`, the list of paths its claims name. A review that did not run this Phase 6 — a deferred review a Stop adopted, for example — writes `not run — <reason>` in each Phase 6 field it did not produce, never `none`, which reads as a clean audit. Then run `node "{plugin_root}/hooks/lib/review-packet-v1.js" create --root "{project_root}" --session "{session_id}" --input "<that file>" --baseline "$BASELINE_SHA"` with the `{session_id}` step 5b resolved; with a receipt it takes the baseline the step 5b audit recorded, refuses a `--baseline` that differs from it, and removes the input file once it has read it, so write the file again before another `create`. It refuses unless this chain waits for its review, checks the step 5b receipt against the current tree (a stale receipt is refused with the audit command to run; a receipt that records unlanded, pending or unverified claims, or whose latest audit did not complete, is carried, never cleared; a chain whose bypass ledger records the edit-landing escape, and a deferred review that ran no audit, get their packet without a receipt), takes `changed_files` from the canonical change set, binds the tree, and prints the block from `REVIEW PACKET v1` to `END REVIEW PACKET v1`, whose first field line is `policy: reviewer-readonly-v1`, with its sha256; `review-packet-v1.js show --root "{project_root}" --session "{session_id}"` prints it again. Paste that block unchanged and unindented into EVERY reviewer prompt of this round: each aspect, persona and judge run and the consume reviewer. Whatever one spawn needs beyond it — its perspective, a `review_scope:` line, `merged_panel_findings`, `findings_ledger`, `external_review`, `judge_run: second` — goes outside the block. The packet carries evidence only; it grants no capabilities. The post-review hook records every reviewer run against the block, says right away when a run saw another block, and refuses the consume review while the latest run of any reviewer saw another block, while the tree, the change set or the receipt changed after `create`, or while a primary judge step 4b requires has no substantive report on it; re-spawn what its refusal names. `/zensu:cover` and a review outside an implementation-complete chain cannot run `create`; they build the block by hand with the same policy line and fields.
    3. **Review fan-out (read-only, parallel).** **External review import, first review only:** when `hooks.reviewJudge` resolves `on` (step 4b) and no post-review directive named a fix round, a Workflow review is imported only when it ran the plugin's own template. Then launch the file its `script=` names (the rest of that line) through the Workflow `scriptPath`, never an edited script and never the template pasted into the inline `script` input (the import answers `foreign-script` unless the launched script is the template byte for byte; a launch the tool refuses means no Workflow review: spawn the batch below), with `args` an object of `tree` (the `tree=` value of the same line), `lenses` (the perspectives the panel and activation commands below name, plus `tests` when they lack it), `changedFiles` (the step-2 list), `packet` (the step-2c block, verbatim), `ceiling` 10, `perLensCap` 8 and `knownDeferred`; its finders and refuters run as `zensu:review-aspect`, confined to `reviewer-readonly-v1` like the panel. It answers `status=ok` only when one recorded launch came after the newest change to the change set, its run completed the shipped template with a `changedFiles` list naming every changed path, and its result parses as `zensu-review-result/v1` and names the current tree; `degraded` when the run journal shows a failed, lost or miscounted agent or a finder failed — append its `EXTERNAL REVIEW DEGRADED` line as well, carry it into the CHAIN-END SUMMARY, and import anyway; a result of any other shape answers `status=unavailable reason=foreign-shape`, so the batch below runs. When several launches are fresh and none matches the output file, it answers `reason=ambiguous-launch`; re-run it with `--launch <id>` of the `launch` line whose `task=` names that file. On `ok` or `degraded`, skip the aspect batch below, log `PANEL SKIPPED — external review <name> imported`, for each `gap <lens> finder-failed` line spawn ONE `zensu:review-aspect` with that perspective over the step-2c block, or log `REVIEW GAP — <lens> (finder failed)` when the lens is no perspective, and continue with step 2b's personas and step 4; `none`, `stale`, `off` and `unavailable` leave this step exactly as written, a workflow still running is waited for and never imported half-done, and a re-review never imports. Otherwise spawn ONE parallel batch (the review fan-out the main-thread model above sanctions, as it sanctions step 4b's judge pair): one `zensu:review-aspect` agent per perspective of the panel that `ZENSU_ROOT="{plugin_root}" CLAUDE_PROJECT_DIR="{project_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_review_panel'` prints — `lean` (the default): `correctness`, `design`, `security`; `full`: `conventions`, `bugs`, `architecture`, `tests`, `security` — and resolve `hooks.aspectActivation` with `ZENSU_ROOT="{plugin_root}" CLAUDE_PROJECT_DIR="{project_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_hook_enabled aspectActivation && echo on || echo off'`. On `on` (the default) pipe THIS round's reviewed paths (the `review_scope:` list when one applies, otherwise the packet's `changed_files`, one path per line) into `node "{plugin_root}/hooks/lib/aspect-activation-v1.js" --panel <panel> --round <round>` first; on `off` pipe an empty change set (`printf ''`) into the same command instead and log `ASPECT ACTIVATION OFF — hooks.aspectActivation`, so no perspective is skipped for what the change set holds while the panel's own re-review shape still applies. Either way `<round>` is `re` on a re-review the post-review directive launched and `first` otherwise, and you spawn only the perspectives it answers `spawn`. The lean panel skips `security` on a documentation-only change set and re-reviews a fix round with `correctness` alone, by design; the full panel skips at most `architecture` on a change set carrying no production code and `tests`/`security` on a documentation-only one; both fail OPEN on empty or unclassifiable input, so a narrowed panel is always a proven reduction and never a guess. Log every `skip <aspect> <reason>` line as `ASPECT SKIPPED — <aspect> (<reason>)` and carry the count into the final report — a panel that shrank silently is indistinguishable from one that was never spawned. A FAILING command (node missing, non-zero exit) is different: log `ASPECT ACTIVATION UNAVAILABLE — <reason>` and spawn the whole panel — PLUS one agent per step-2b `spawn <name>` persona (Agent tool, `subagent_type=<name>`; its findings MUST carry the persona's uppercased `<NAME>-` ID prefix per the README persona contract). Give every batch member the step-2c block unchanged and name its perspective (or persona) outside it. The built-in aspect agents receive enforced `reviewer-readonly-v1`: `Read`/`Grep`/`Glob` only, no Bash/build/test, no workflow mutation, and no nested agents. Repo-local custom personas remain neutral `host-profile-v1`; audit and constrain their own `tools:` frontmatter to the same read trio and repeat the no-mutation/no-nesting contract in the spawn prompt. **A repo-custom persona's prompt is repo-authored, so it carries no evidence-discipline block of its own** — unlike every plugin agent, and unlike the confined workers `/zensu:pr-team-review` and `/zensu:plan-review` spawn their custom seats as. Read the canonical block at run time from `{plugin_root}/docs/evidence-discipline.md` (the delimited `<!-- zensu:evidence-discipline -->` … `<!-- /zensu:evidence-discipline -->` region, verbatim, never a copy pasted into this skill) and prepend it to every custom persona spawn prompt, ahead of the REVIEW PACKET. Read the severity rubric the same way from `{plugin_root}/docs/review-severity.md` (the `<!-- zensu:review-severity -->` … `<!-- /zensu:review-severity -->` region) and prepend it right after the evidence-discipline block, so a persona rates findings on the same scale as the built-in aspects; the rubric has no second carrier, so when its file is unreadable log `PERSONA CARRIER UNAVAILABLE — review-severity: <reason>` and spawn anyway. If a persona spawn fails because the subagent type is not registered, log `PERSONA SKIPPED — <name> (not registered)` and continue the batch.
    4. **Merge in-thread.** Collect every `## Aspect:` findings list plus every custom persona's list, deduplicate (same `file:line` raised by multiple perspectives → keep the highest confidence), and sort CRITICAL → IMPORTANT → SUGGESTION → by file path. On the import path, merge every `EXT-<n>` finding between the `findings … begin` and `end` lines the import printed too, none dropped and none labelled rejected — a `refuted` or `unverified` one included, its `verification` state and the refuter's reasoning kept in its evidence: rewrite it in the aspect line shape as `EXT-<n>`, re-anchor it on the current tree, map its severity onto `docs/review-severity.md` (raise it when the evidence demands, never lower it), give it its `R<k>-F<n>` id beside the `EXT-<n>` label, and keep a finding without a `file:line` anchor in the merged list with the anchor `-`, so the consume reviewer and the findings ledger carry it like any other.
    4b. **Judge second pass (config-gated).** On a re-review with the lean panel, skip this step: the judge reviews the first review only. Otherwise resolve the flag with the real merge semantics: `ZENSU_ROOT="{plugin_root}" CLAUDE_PROJECT_DIR="{project_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_hook_enabled reviewJudge && echo on || echo off'`. Merge the deltas BEFORE fix routing: a `Panel-FP:`-prefixed meta-verdict neutralizes the finding it references — keep BOTH visible in the merged list, retitle the referenced finding `[Panel-FP-neutralized — do not fix]` and set it to SUGGESTION (a referenced CRITICAL is never dropped outright, only annotated + downgraded), and exempt neutralized items from fix routing in EVERY severity mode, including `autoFixIncludeSuggestions`; every other JUDGE finding joins the list normally and takes the next free `R<k>-F<n>` id after the panel findings, beside its `JUDGE-n` label (a finding that quotes an earlier ledger id still takes its own new id), except a covers line (`[STILL OPEN] <id> covers <panel-id>`, `[NOT FIXED] <id> covers <panel-id>`): it is a meta-verdict like `Panel-FP:`, takes no id, and names the panel finding it covers — a `[STILL OPEN]` line keeps that finding under the earlier ledger id, a `[NOT FIXED]` line leaves it its own id. On the import path the judge ALWAYS runs: append the optional `external_review` input after `merged_panel_findings` — the workflow's name, the active panel's perspectives (step 3's panel and activation commands still name them) and the lenses the workflow reviewed (the `lenses=` field of the import's first line) — and it answers a `## Gaps` section; for each `- GAP <perspective> <path>[, <path>...] — <reason>` line spawn ONE `zensu:review-aspect` with that perspective over the step-2c block unchanged, with the gap paths on a `review_scope:` line after it, all gap aspects in one batch of their own, merge their findings like the panel's under the next free ids after the judge's, with no second judge pass, and log `REVIEW GAP — <perspective> <paths> — <reason>`, while the judge keeps the full cumulative `changed_files`. A judge that fails, answers `REVIEW PACKET INVALID` or returns no parseable `## Gaps` section means no coverage check ran: log `REVIEW GAP UNAVAILABLE — <reason>` and spawn step 3's panel over the step-2c block, then run this step's judge over the panel's merged findings as on the panel path. **Independent second run, first review only:** when no post-review directive named a fix round, resolve the flag the same way with `zensu_hook_enabled reviewJudgeSecondRun`; on `on` (the default), the tool message that spawns the judge also spawns a second `zensu:review-judge` with the identical input plus a last line `judge_run: second`. The second run only adds findings, labelled `JUDGE-B<n>`, and you enforce that here: a `Panel-FP:` line, a `[NOT FIXED]` or `[STILL OPEN]` tag or a `## Gaps` section in its report neutralizes, re-ids and gaps nothing; log each as `JUDGE SECOND RUN RULE BREACH — <what>` and merge only its findings, so on the import path the gap list and its fallback above stay the first run's. Merge the union after the first run's deltas: a `JUDGE-B<n>` finding naming the same defect at the same `file:line` as a merged finding that is not `[Panel-FP-neutralized — do not fix]` adds its label to that finding and raises its severity when the second run rated it higher; every other one, one that names the defect of a neutralized finding included, takes the next free `R<k>-F<n>` id at its own severity. A second run that fails, answers `REVIEW PACKET INVALID` or returns no parseable report leaves the first run's result standing: log `JUDGE SECOND RUN UNAVAILABLE — <reason>` and carry it into the final report. Flag disabled → the first run stands alone, as before. **The primary judge is a prerequisite of the consume review** whenever this step runs it: a primary run that fails, answers `REVIEW PACKET INVALID`, or returns no `## Aspect: judge` heading with a `JUDGE-<n>` finding or `- (no findings)` gets exactly ONE more run on the same block — on the import path that retry is the panel path's judge after the fallback panel — and a second failure stops the chain: keep both results, do not spawn the consume reviewer, and report the chain as pending. The second run never stands in for the primary, and the post-review hook refuses a consume review that lacks a substantive primary report on this round's block.
    4c. **Finding Verification Gate (main thread, config-gated).** Resolve the flag the same way: `ZENSU_ROOT="{plugin_root}" CLAUDE_PROJECT_DIR="{project_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_hook_enabled findingVerification && echo on || echo off'`. On `on` (the default), grade the merged list before any of it routes to a fix — the panel findings AND the step-4b `JUDGE-*` deltas, because a judge delta is agent output too. Nothing here is delegated: **you** verify, in this thread, because a verifier subagent would only be one more process that can hallucinate. **Stage 1 (deterministic, model-free):** with the Write tool, write `{project_root}/.zensu/reviews/findings-round-<n>.json`, where `<n>` counts this chain's reviews from 1 so every round writes a new file, as `{"changedFiles":["<every path of the step-2 change set>"],"findings":["<one string per merged finding, in merged order>"]}`. Each finding's whole text is one JSON string, so newlines, quotes, backticks, `$(…)` and a line reading `FINDINGS` stay data. Then run `node "{plugin_root}/hooks/lib/finding-verify-v1.js" --root "$TOP" --input "{project_root}/.zensu/reviews/findings-round-<n>.json"`; it removes the file once it has graded it. Never put finding text into a shell argument, a command substitution or a heredoc: a quoted heredoc still ends at a payload line equal to its delimiter, and the shell then runs the lines after it. It answers `anchor-ok`, `off-changeset`, `line-out-of-range`, `phantom-path`, `out-of-root`, or `no-anchor` per indexed finding, then a `summary` line, and always exits 0 — a verdict is data, not a gate. **Read that summary honestly:** `total=` MUST equal the number of strings in `findings`; an `invalid-input <reason>` line, a `truncated` line, a mismatch, a missing `node`, a non-zero exit, or unparseable output is NOT a pass — correct a malformed file and run it once more, then log `FINDING VERIFICATION DEGRADED — <reason>`, skip Stage 1, and still do Stage 2 by hand. An empty `findings` array is clean only when the summary carries no `invalid-input` line. Never fail the gate closed — a wedged review chain is strictly worse than an ungraded finding. Every `EXT-<n>` and gap-aspect finding is graded like a panel finding, and `CHANGED-FILES` stays the full step-2 set even when a gap packet was narrowed. **Stage 2 (your own read):** for every `anchor-ok` / `off-changeset` finding, `Read` the cited region (`offset` = max(1, line − 10), `limit` = 25) and grade the finding's OWN `Evidence:` claim against what is actually there — `VERIFIED` when the cited code says what the finding says it says, `UNSUPPORTED` when the region does not support the claim; a hard Stage-1 verdict is `PHANTOM` without a read; `no-anchor` meta-verdicts (`Panel-FP:` and the like) are exempt, and an `EXT-<n>` finding the merge kept with the anchor `-` is never neutralized either, because a missing anchor is not a hallucinated one; nothing can grade it, so retitle it `[Deferred — do not fix]` with its original severity in its text, set it to SUGGESTION so no severity mode routes it, ledger it with the anchor `-` (`parked` when IMPORTANT, `deferred` otherwise) when `hooks.reviewConvergence` is on, and list it under `## Open`; an `off-changeset` finding is NOT wrong by itself — a reviewer may legitimately cite an unchanged caller — it only makes the read mandatory. **Neutralize, never delete:** every non-`VERIFIED` finding KEEPS its place in the merged list, is retitled `[Unverified — do not fix]`, is set to SUGGESTION, and is exempt from fix routing in EVERY severity mode including `autoFixIncludeSuggestions` — exactly the mechanics step 4b uses for `Panel-FP`, and for the same reason: a silent drop would let this gate kill a real CRITICAL with no trace. A referenced CRITICAL is annotated and downgraded, never removed, and the two annotations may coexist on one finding. **Stage 3 (reproduction, re-reviews only, config-gated).** Resolve the flag the same way with `zensu_hook_enabled criticalReproduction`. On `on` (the default), and only when this review is a re-review (the post-review directive named a fix round), reproduce every CRITICAL finding that Stage 2 graded `VERIFIED` before it may route: write a test that exercises the cited behavior and must fail on the current tree OUTSIDE the project tree (the session scratch directory, or the system temp directory), reaching project files by absolute path, because the review packet binds the working tree and a test file written into it makes the consume review refuse the round; run it with `CLAUDE_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --evidence-run --scope scoped --cmd '<that test>' --log {log_file}`, and log `FINDING REPRODUCTION — <ledger-id> <REPRODUCED|NOT-REPRODUCED|NOT-TESTABLE> <record id or one-line reason>` (the merged finding id when no ledger is kept) through the quoted-heredoc `append --message-stdin` form the ledger lines use. `REPRODUCED` — the run failed for the cited reason: the finding routes, and the fix round adds that test to the project as its regression test. `NOT-REPRODUCED` — the run passed: retitle the finding `[Deferred — do not fix]` with `CRITICAL (not reproduced)` in its text, set it to SUGGESTION so no severity mode routes it, list it under `## Open`, and add the test to the project only when it asserts behavior the spec requires, in the next fix round or the terminal self-review. `NOT-TESTABLE` — no test can express it, for example a secret written to a log: retitle it the same way with `CRITICAL (not testable: <reason>)` in its text and list it under `## Open` for a human. Never delete a finding here. Flag disabled → re-review CRITICAL findings route as before. Log `FINDING VERIFICATION — {n} verified, {n} unsupported, {n} phantom, {n} off-changeset` and carry it — and any `DEGRADED` line, which is not a clean state — into the final report AND the CHAIN-END SUMMARY. Flag disabled → skip straight to step 5.
    5. **Thin consume-mode spawn (the single hook trigger).** Immediately before every ticket/spawn, a bound chain MUST read fresh `--autopilot-status` and require the current session owner, `stage=TDD_RUNNING`, `tdd.sessionId`, `tdd.attempt`, `tdd.chainId`, and `tdd.returnStage` to match `RUN_ID`, `ATTEMPT`, `CHAIN_ID`, and `RETURN_STAGE`; stale or incomplete evidence blocks before the ticket is issued. Then spawn ONE `zensu:code-reviewer` with the Agent tool (`subagent_type='zensu:code-reviewer'`, `run_in_background: false`).
