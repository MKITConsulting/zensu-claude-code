Zensu · Multi-Repo

Identity stays one. Reach is declared.

The whole multi-repo proposal rests on a single distinction: what the session is exists exactly once. Where it may reach is a declared list. And what it must verify is always that same list — never less.

The three rules everything else follows from

Rule 1

Identity is never multiplied

One record, one state directory, one log, one resume point, one doctor view. The moment a second root carried identity there would be two truths about which session this is, and no rule for which one wins.

Rule 2

Reach is declared, never inferred

The list is written once at arming and is immutable afterwards. It may not come from a plan, a specification, or a review comment. A root the model can name is a confinement the model can leave.

Rule 3

Evidence duty follows reach

Every site that judges sees exactly the set that may be written to. If one check falls behind the reach, the chain reports success for work it never saw — which is today's defect, only larger.

What follows immediately

The anchor is also a code root, but no code root is ever an anchor.
That is why the resume point stays the anchor. A resume inside a satellite would present a different CLAUDE_PROJECT_DIR, and the session would no longer bind.
The list governs two confinements, not one.
It opens Bash write access and reviewer read access. Both are capability grants, not settings — hence one list, one validation, one moment.
One more field in the workflow document costs a minor release.
The runtime-lineage rule makes every schema change a breaking change while the plugin is at major 0.
Without a list, everything behaves exactly as it does today.
With codeRoots[] absent, the union is the anchor alone. That is the state of every existing chain and must remain so.
