Zensu · design sketch

Anchor and satellites

How a Zensu chain could span several repositories without giving up the one trusted project root — and how a review sitting on top of it can see contract breaks between those roots.

1 Today: everything hangs off one anchor

The project root comes from the immutable Session Control record. Every consumer in the chain asks that same place, and anything outside it does not exist for the chain.

2 What that produces

Three findings, each read at the cited site. The third is the dangerous one, because it does not block — it reports green.

Receipt

Two runs, no usable receipt

The audit writes to <--project>/.zensu/state/ while the terminus looks in the anchor's state directory. Two runs therefore leave two receipts nobody reads — and each run reports the other repository's claims as not landed.

zensu-edit-landing.sh:266 · zensu-log.sh:572

Asymmetry

Edit writes across, Bash does not

Rule (B) of the write gate denies every Bash write outside the root. The edit gate only classifies a path as state, zensu or other and does not confine it. The topology is half blocked.

bash-source-write-parse.js:808 · pre-edit-tdd-reminder.sh:161

Silent pass

The terminus checks nothing

The receipt gate fires only when git -C "$CLAUDE_PROJECT_DIR" counts changes. With a clean orchestrator the count is zero, the receipt is skipped, and the chain closes — with a reviewer that saw nothing either.

3 Proposal: one anchor, several code roots

The anchor is unchanged and keeps everything that carries identity and state. A declared list of further roots is added, read by a small set of consumers.

4 The five consumers

That is all of them. Everything else — record, state directory, logs, phase gate, doctor — stays untouched at the anchor. The first four carry multi-repo; the fifth carries the cross-root review of section 5.

5 Cross-root review as its own stage

Each root finishes its own review exactly as today. Only then does a new, single stage run that looks solely at relations between roots — and then the chain closes.

Why this stage is mode-independent.

The review chain runs in full under vanilla — fan-out, judge second pass, Finding Verification Gate, the consuming reviewer and the self-review terminus are all listed among what runs “exactly as written” (tdd/SKILL.md:193). The decisive difference from the mechanical audit: a reviewer reports a finding, it does not demand a characterization test. That demand is precisely why the Cross-Layer audit cannot run in vanilla.

The exception is data-driven, not blanket.

The capability confinement is not opened but redirected: what is allowed is the union of the codeRoots frozen at arming — not “anywhere”. It still confines, only to a previously declared area. This stage's lease carries exactly that list, and the per-repo reviewers keep their narrower confinement.

The expensive part is the chain state machine.

An extra stage between convergence and terminus means a new chain shape in classifyChain(). The repository conventions name roughly eight consumers that must travel with it: --chain-status, --chain-recover, the refusal-hint renderer, the Stop enforcer, the doctor renderer, the ticket issuer, the rearm writer and the reviewRearm validator.

The validator is the critical one: on an unexpected key set it rejects the entire workflow document and fails every hook closed. A schema change has to land there first.

A complement, not a replacement: the mechanical detector

Step 6b could be split.

Part (a) verifies the plan's Cross-Layer table and is rightly skipped in vanilla — the table is never populated there. Part (b) only scans the diff for newly added field and payload literals and demands nothing. It could run in vanilla at warning level, exactly as step 6c already does.

That is a cheap mechanical precursor to the cross-repo review, not a substitute for it.

6 Transferability via /zensu:session-trail

A multi-root session still has exactly one cwd and one transcript, so list, show, handoff and takeover keep working. What degrades is not transferability but the accuracy of what they report.

Handover

The brief reports a clean tree

gitState(cwd, full) takes a single path, and that path is the anchor. The anchor is clean while the changed files sit in the satellites, so a takeover brief would claim no uncommitted changes for a session with a dirty tree in two other repositories — the same silent green as section 2, relocated into the handover path.

trail.mjs:769

Discovery

Visible only under the anchor

list keeps only transcript directories whose name starts with the slug of the repo's main checkout. From a code root's repository the session is reachable only via --all, otherwise only from the anchor. Pre-existing behavior that multi-repo makes more consequential.

session-trail/SKILL.md:152

Resume

Already correct today

The printed continuation line cd ${r.cwd} && claude --resume … lands in the anchor. That is exactly the right place and needs no change.

trail.mjs:1067

Constraint: resume always in the anchor.

A resume inside a code root would present a different CLAUDE_PROJECT_DIR. The Session Control record would no longer match and the session would bind as orphaned or not at all. The printed resume line must therefore never point at a satellite, however plainly the work lives there.

The fix costs no schema.

trail.mjs has no write channel. It may read the anchor's workflow document, take codeRoots[], and call gitState once per root. No new registry, no change to ~/.claude, no lineage cost. That places it in stage 2, not stage 3.

7 Two non-negotiable constraints

The root list is frozen at arming.

It belongs in the workflow document, exactly like today's vanilla flag — never in an environment variable and never derived from model-authored text. It governs the write gate and the capability confinement: extending it is a capability grant, not configuration. Every root must canonicalize, be a real work tree, and be neither a parent of the anchor nor a filesystem root.

One field in the workflow document costs a minor release.

The repository's runtime-lineage rule makes every schema change a breaking change while the plugin sits at major 0. A patch would make a compatibility promise the code cannot keep. This holds for codeRoots[] as much as for the new chain shape.

8 Staging

Stage one closes the silent pass and needs no new field. Stage two makes multi-repo usable. Stage three delivers the actual payoff.

Stage 1

Detect and refuse

no schema change · patch

  • A claim resolving outside the anchor fails the audit instead of passing silently.
  • The terminus checks the receipt even when the anchor is clean.
  • A doctor row naming the topology.
  • The chain stays single-rooted — it just stops lying.
Stage 2

Declared code roots

schema change · minor

  • codeRoots[] in the workflow document, written at arming.
  • Root labels in the claim format and in the merged receipt.
  • The four multi-repo consumers from section 4.
  • Validation of each root before it enters the write gate or a lease.
  • session-trail reads codeRoots[] and calls gitState per root so the handover brief is true.
Stage 3

Cross-repo review

new chain shape · minor

  • A new stage between per-repo convergence and terminus, once per chain.
  • Its own reviewer type, leased to the root union.
  • Capability confinement data-driven rather than blanket.
  • A new shape in classifyChain() plus its eight consumers.
  • Optionally preceded by step 6b part (b) at warning level.
