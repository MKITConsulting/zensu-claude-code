Zensu · design sketch

Anchor and satellites

How a Zensu chain could span several repositories without giving up the one trusted project root — and how a review sitting on top of it can see contract breaks between those roots.

Status: stage 1 is implemented; stages 2 and 3 are REDESIGNED, NOT BUILT. Stage 1 ships the detect-and-refuse half: the terminus judges the edit-landing receipt's verdict, a logged claim arms that requirement even when the anchor's tree is clean, a claim resolving outside the audited root fails the audit and names the foreign root, and /zensu:doctor carries a topology row. Which half of stage 1 is universally live is narrower than “stage 1 is implemented”: the log writer redacts a message before it lands, rewriting $HOME to ~ and the project root to <project>, and the audit's absolute-claim arm only ever sees a path still beginning with /. A foreign root outside every home directory and the project root is detected; a sibling repository under $HOME is rewritten out of that shape and is not, and one under another user's home or /root becomes <home> and names no root either. Nothing else here is implemented. On 2026-10-21 stages 2 and 3 were redesigned. The sealed carrier the specification's §6.1.1 chose on 2026-09-20 is superseded, because its premise moved: the Bash source-write gate it guarded became opt-in and off by default on 2026-10-03. The list of code roots, codeRoots, now lives in the workflow document as a validated declaration that bounds accidents, not intent — the bar the receipt and the run log beside it already meet. The cross-repo check becomes one more perspective of the review fan-out instead of a new stage. Read the staging below as designed work that ships in five pull requests behind a dark-launch switch, not as behavior.

1 Today: everything hangs off one anchor

The project root comes from the immutable Session Control record. Every consumer in the chain asks that same place, and anything outside it does not exist for the chain.

2 What that produces

Three findings, each read at the cited site. The third is the dangerous one, because it does not block — it reports green.

Receipt

Two runs, no usable receipt

The audit writes to <--project>/.zensu/state/ while the terminus looks in the anchor's state directory. Two runs therefore leave two receipts nobody reads — and each run reports the other repository's claims as not landed.

Asymmetry

Edit writes across, Bash only when the gate is off

While the opt-in write gate is on, its rule (B) denies a Bash source write outside the root. The edit gate only classifies a path as state, zensu or other and does not confine it. With the gate on, the topology is half blocked.

Silent pass — superseded by stage 1

The terminus checked nothing

The receipt gate fired only when the anchor's change count was non-zero. With a clean orchestrator the count is zero, the receipt was skipped, and the chain closed — with a reviewer that saw nothing either. Stage 1, item 2 supersedes this: the gate now ALSO arms on a logged claim, and it judges the receipt's clean verdict rather than its existence. Two details the earlier wording got wrong about --tdd-complete: the count resolves its root through zensu_resolve_project_dir() rather than the ambient CLAUDE_PROJECT_DIR, and it runs with the git environment scrubbed. The --chain-done zero-change terminus now counts the same way. A chain that claimed nothing is still exempt.

3 Proposal: one anchor, several code roots

The anchor is unchanged and keeps everything that carries identity and state. A declared list of further roots is added, and the consumers that enumerate, count or confine read the union.

The anchor need not be a repository. A session started in a plain folder that holds several repositories has a folder anchor: it keeps the session's state but has no change set of its own, so every file a chain changes there must sit in a declared code root. Section 6.5 of the specification states the rules.

4 The consumers that read the union

These are the consumers whose ENUMERATION or CONFINEMENT changes most visibly: the first four carry multi-repo, the fifth lets the reviewers of section 5 read the declared roots. The specification's §6.3 lists the rest — the full suite and its CI deferral, acceptance verification, finding verification, the protected .zensu directories, the doctor row and session-trail, which section 6 covers. The Session Control record, the workflow document and the run log stay with the anchor.

5 Cross-root review as one more perspective

The redesign adds no stage. The review fan-out reads the union, one more perspective, crossrepo, looks solely at relations between roots, and the chain then closes exactly as today.

Why this perspective is mode-independent.

The review chain runs in full under vanilla — fan-out, judge second pass, Finding Verification Gate, the consuming reviewer and the self-review terminus are all listed among what runs “exactly as written” (skills/build/references/modes.md:7). The decisive difference from the mechanical audit: a reviewer reports a finding, it does not demand a characterization test. That demand is precisely why the Cross-Layer audit cannot run in vanilla.

The exception is data-driven, not blanket.

The capability confinement is not opened but redirected: what is allowed is the anchor plus the declared roots — a list arming validated and every read re-checks as strings — not “anywhere”. It still confines, only to a previously declared area, and a direct read of every .zensu below the anchor or in a declared root is refused; a search rooted above an undeclared nested work tree still reaches that tree's .zensu, a residual the specification names. No reviewer needs a lease of its own: the main thread already reads any of these files, so a reviewer that reads a validated work tree gains nothing the session lacks.

No new chain shape, so the state machine stays as it is.

The 2026-09-20 design put a stage between convergence and terminus, which meant a new chain shape in classifyChain() and roughly eight consumers travelling with it, the reviewRearm validator the critical one: on an unexpected key set it rejects the entire workflow document and fails every hook closed.

A perspective needs none of that. chainShape reads workflow flags and the rearm receipt, never panel state, and the fan-out runs in the main thread before the one ticketed reviewer spawn, so a multi-root chain classifies exactly as a single-root chain does.

A complement, not a replacement: the mechanical detector

Step 6b could be split.

Part (a) verifies the plan's Cross-Layer table and is rightly skipped in vanilla — the table is never populated there. Part (b) is a mechanical diff scan for newly added field and payload literals, and it is skipped for one reason only: it lives inside the same step as part (a). Marking Phase 6 NOT complete is not itself what keeps it out — the Precondition Drift Audit does the same and runs in vanilla. What part (b) inherits is the remedy: its finding text asks for a paired characterization, a test vanilla cannot produce. Making it vanilla-safe therefore needs two edits, not one — downgrade it to warning level as step 6c already is, AND reword the finding so it reports the unpaired literal without demanding the pairing.

6 Transferability via /zensu:session-trail

A multi-root session still has exactly one cwd and one transcript, so list, show, handoff and takeover keep working. What degrades is not transferability but the accuracy of what they report.

Handover

The brief reports a clean tree

gitState(cwd, full) takes a single path, and that path is the anchor. The anchor is clean while the changed files sit in the satellites, so a takeover brief would claim no uncommitted changes for a session with a dirty tree in two other repositories — the same silent green as section 2, relocated into the handover path.

trail.mjs:2839

Discovery

Visible only under the anchor

list keeps only transcript directories whose name starts with the slug of the repo's main checkout. From a code root's repository the session is reachable only via --all, otherwise only from the anchor. Pre-existing behavior that multi-repo makes more consequential.

skills/session-trail/references/limits.md:12

Resume

Already correct today

The printed continuation line cd -- ${r.cwd} && claude --resume … lands in the anchor. That is exactly the right place and needs no change.

trail.mjs:5027

Constraint: resume always in the anchor.

A resume inside a code root would present a different CLAUDE_PROJECT_DIR while the recorded project_root still exists — and a present-but-different root is never relaxed, because the orphaned relaxation requires the recorded path to be absent. So the session would not bind as orphaned; it would simply be denied. The printed resume line must therefore never point at a satellite, however plainly the work lives there.

The fix costs no schema — but it is not free.

This fix adds no write of its own — trail.mjs's only write channel is the lineage ledger. It may read the anchor's workflow document, take the root list, and call gitState once per root. No new registry, no change to ~/.claude, no lineage cost. That places it in stage 2, in the pull request that also carries the review side.

The cost worth naming, as §6.4 of the specification insists: trail.mjs may run outside any session and outside every hook, so teaching it to read the root list makes it one more consumer of a model-declared list, running git -C in paths that list names. It therefore reads the list through the same validating reader as every other consumer, and runs git with the read-only prefix that takes no index lock and runs no fsmonitor hook.

7 Two constraints — and how the redesign meets them

The root list is validated at arming, and it bounds accidents, not intent.

The 2026-09-20 design treated the list as a capability grant: it governed the Bash write gate and the reviewer confinement, so it had to come from the operator and live where the session could not rewrite it. Both premises moved. The write gate became opt-in and off by default on 2026-10-03, and a reviewer that reads a validated work tree gains nothing the main thread lacks, because the main thread already reads those files.

So the list is a declaration held to the bar of the receipt and the run log beside it: codeRoots in the workflow document bounds accidents, not intent. Every root must canonicalize to the top of a git work tree, be neither the anchor, an ancestor of it nor a filesystem root, be neither the home directory nor one of its ancestors, stay clear of the plugin, its data and the operator's configuration in both directions, and overlap no other live session or chain. A rejected entry refuses the arming. Every read re-checks the rules a string comparison decides, so a hand edit into a shape they refuse falls back to the anchor alone; the overlap with other sessions is judged at arming only.

The sealed pair of §6.1.1 — the Session Control record for integrity, an interactive confirmation at arming for provenance — stays documented as history and as the path to a later strict-evidence mode. §8.1 states why even that pair would not have bought intent resistance: the record does not authenticate its own contents either.

One field in the workflow document costs a minor release.

The repository's runtime-lineage rule makes every schema change a breaking change while the plugin sits at major 0. A patch would make a compatibility promise the code cannot keep. This holds for codeRoots[], and the redesign adds no chain shape that would cost a second one. The set ships as one minor in five pull requests, and arming refuses --code-root until the last of them flips the dark-launch switch.

8 Staging

Stage one closes the silent pass and needs no new field. Stage two makes multi-repo usable, and since the redesign it also carries what stage three was for: the cross-repo check.

Stage 1

Detect and refuse

no schema change · patch

  • A claim resolving outside the anchor fails the audit instead of passing silently.
  • The terminus checks the receipt even when the anchor is clean.
  • A doctor row naming the topology.
  • The chain stays single-rooted — it just stops lying.
Stage 2

Declared code roots

workflow-state field · minor · five pull requests

  • codeRoots[] declared at arming with --code-root, validated then, re-checked as strings on every read, and kept in the workflow document as a declaration that bounds accidents, not intent.
  • The @label/ spelling in claims, round scopes, ledger anchors and the packet.
  • Every consumer from section 4, the capability confinement included, plus the full suite, acceptance verification and the doctor row per root.
  • Every root's .zensu protected, a direct read of any .zensu below the anchor refused, and every git call into a code root read-only.
  • session-trail reads codeRoots[] and calls gitState per root so the handover brief is true.
Stage 3

Cross-repo review

folded into stage 2 · no new chain shape

  • One more perspective, crossrepo, inside the existing review fan-out.
  • Spawned only for a chain with code roots; a single-root chain prints nothing new.
  • No reviewer type, no lease and no shape in classifyChain() of its own.
  • Optionally preceded by step 6b part (b) at warning level.
