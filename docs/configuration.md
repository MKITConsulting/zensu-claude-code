# Configuration

Every hook, every config flag, the merge order, and the environment
variables Claude Code supplies. Nothing here is required to run the plugin —
defaults are the supported configuration.

### Hooks (24)

| Hook Script | Event | Config Flag | Description |

| `session-start-session-control.sh` | SessionStart + SubagentStart | — | SessionStart creates the immutable Session Control v1 record and emits the principal-specific context; it neither reads nor writes `CLAUDE_ENV_FILE` and exports no plugin-private selectors to model or subagent shells. A payload with neither `agent_id` nor `agent_type` receives interactive `main-v1`; `claude --agent` SessionStart payloads use the same exact reviewer/neutral classifier as later tool hooks. SubagentStart reads the parent record and injects `reviewer-readonly-v1` for the five exact plugin-scoped reviewers (`code-reviewer`, `review-aspect`, `review-judge`, `plan-review-worker`, `pr-review-worker`) or neutral `host-profile-v1` for every other child, including `zensu:zensu-plm`. Because Claude Code cannot block on SubagentStart, this hook's child-side failure is diagnostic; the first PreToolUse gate performs the mandatory fail-closed revalidation. Stateful model commands receive Claude's native plugin root/data values at the call site and validate the host-exposed session id against this record inside the helper process only. |
| `pre-reviewer-capability-gate.sh` | PreToolUse `*` | — | First enforcement hook for every tool. Derives and revalidates session id, installed plugin root, plugin-data store, private record, workflow-state anchor, current canonical `cwd`, and live runtime digest directly from standard hook metadata; it never assumes SessionStart shell exports reach hook processes. Missing or mismatched bindings return a structured `permissionDecision: deny`; launcher/runtime failures are normalized to Claude's blocking exit code 2 with a sanitized diagnostic. The five exact plugin-scoped reviewers and `zensu:zensu-plm` may invoke only `Read`/`Grep`/`Glob`; plan/PR workers are further limited to their private exact-file/safe-subtree lease and all leased paths are revalidated against their creation snapshot on every call. Only the top-level interactive thread receives `main-v1`. Other `host-profile-v1` children retain ordinary non-command host tools, while all shell/command aliases, direct or ancestor traversal into Session Control/workflow-root state, mutations below the installed-plugin/private plugin-data roots, and mutating Zensu operations are blocked. `Grep`/`Glob` require a concrete safe subtree rather than an omitted path or a project/plugin/plugin-data ancestor. |
| `session-start-evidence-discipline.sh` | SessionStart + SubagentStart | — | **Evidence discipline** (see [Evidence Discipline](architecture.md#evidence-discipline)). Injects the plugin-wide anti-hallucination rule as model-facing `additionalContext` so every process carries it — the main thread and every spawned subagent alike. The directive text is read at run time from `docs/evidence-discipline.md` (the single line between the `zensu:evidence-discipline` markers), never duplicated in the script, so this carrier cannot drift from the block the agents and skills quote; `docs/` is inside the Session Control runtime digest, so that file is tamper-evident within a session — but only while the executing plugin root *is* the recorded one, because `servesRecordedRuntime` lets a compatible sibling install serve a record it did not mint while this hook reads from the executing root, so a mid-session upgrade injects bytes no in-session digest measured (the build-time pins in `tests/structure/test-evidence-discipline.sh` are what bind the text across that case). The load refuses a symlink and then re-checks the file it actually opened — lstat → platform-gated `O_NOFOLLOW`\|`O_NONBLOCK` open → `fstat` dev/ino re-check → size-bounded looped read with an explicit short-read refusal → guarded close — the same hardened reader `user-prompt-best-solution-first.sh` carries. Deliberately unlike `session-start-primer.sh` in three ways: it reads **no config** (there is no opt-out flag; in particular `sessionBanner:false` does not silence it), it has **no fresh-start filter** (it also fires on `resume`/`compact`, where the rule would otherwise vanish with the compacted context), and it applies to **every principal** rather than only `main-v1`. The emitted `hookEventName` echoes the event actually received. Fail-silent by construction: an unknown event, a malformed payload, a missing `node`, or a rule file that is absent, symlinked, swapped between the pre-check and the open, oversized in FILE or in BLOCK, short-read, or malformed exits `0` with no output, so it can never block a prompt or a spawn. The two size bounds are separate: a file far under the file ceiling can still carry one over-long block, and that is refused too. The one branch that is deliberately not silent is the shared plugin-root guard: an inherited `CLAUDE_PLUGIN_ROOT` that does not match the executing plugin refuses with exit `2`. |

| `pre-agent-reviewer-allow.sh` | PreToolUse `Agent`/`Task` | `reviewerSpawnAutoAllow` | Reviewer-spawn grant. It can only **grant or stay silent**: it never emits deny or ask, and every failure path is a silent `exit 0`, because a non-zero exit from a PreToolUse hook would block the spawn outright. | `post-artifact-redact.sh` | PostToolUse `Edit\|Write\|MultiEdit` + `Bash` | — | Artifact path redactor — the net under `zensu-log.sh append`. Consuming repos commit `.zensu/plans/{ts}_tdd-{slug}.md` and `.zensu/logs/{ts}_tdd-{slug}.log` as an audit trail, so both must stay free of absolute developer paths; a scan of ~27k committed log lines across four such repos found no credential values and ~436 lines carrying `/Users/<name>/…`. Both artifacts are model-authored (the plan through the Write tool, a log line potentially through a hand-rolled `printf >>`), so a writer-side helper alone cannot guarantee it. BOTH registered matchers sweep the artifacts modified in the **last 5 minutes**; the write matchers additionally redact the tool's own `tool_input.file_path`, which is the only way an artifact outside that window is reached. Sweeping on the write matchers is not redundancy — the hook is main-principal only, so a SUBAGENT-written artifact is reachable only from a later main-thread pass, and more sampling points mean more chances to catch one inside its own window; the cutoff is the artifact's own mtime and nothing extends it. The window bounds which artifacts are read and redacted, not the enumeration: an entry's mtime is not knowable without a stat, so a candidate regular file costs one syscall before the cutoff can reject it. An earlier revision of this row claimed the window is what keeps the sweep cheap in a repo holding hundreds of tracked plans; it is not. The sweep rejects what it can reject for free (wrong extension, and any entry the dirent already shows is not a regular file) and processes at most `SWEEP_MAX_TARGETS` (25) artifacts per invocation, newest mtime first. There is deliberately no command-text pre-filter: `printf … >> "$LOG"` carries no `.zensu` substring, and a net the one spelling it exists to catch can evade is not a net. A `witness-` prefixed name is excluded **in the `logs` bucket only** — that is where the witness lives, its `cmd` (and only `cmd`) is already redacted by its own writer, and it is the largest file in the directory. The bucket scope is load-bearing: an unscoped exclusion also refused a `.zensu/plans/witness-*.md`, which then kept its absolute developer paths, was reported by nothing, and is not covered by the `.gitignore` fragment this feature ships either. Such a file is an ordinary plan and is swept and redacted like one. The `logs` exclusion is gitignored in THIS repo only, so a consuming repo must add `.zensu/state/` and `.zensu/logs/witness-*.log` itself — the exclusion is not a claim that it never ships. Rules, in order: project root → `<project>`, `$HOME` → `~`, residual `/Users/<seg>` / `/home/<seg>` / `/root` → `<home>`, every rule bounded on both sides. Secret **names** are never redacted — a name grants no access; credential **values** belong to `pre-write-secret-scan.sh`. Containment is canonicalized: a target must resolve to a real `<root>/.zensu/{plans,logs}/<file>` of the bound session's project, compared against the canonical root's own join, so a symlinked `.zensu/logs` cannot carry a rewrite out of the project. `redactFile` opens read-only with `O_NOFOLLOW` and judges the descriptor, refuses a hard link, a non-regular file, a non-UTF-8 body and an oversized artifact, `fsync`s before the rename and abandons it if the artifact changed underneath. The net is disabled entirely while the session cannot bind its Session Control record (an unregistered session, or one whose project root is gone) — that refusal is reported on stderr; a non-main-principal caller is skipped silently, since a subagent call is an ordinary outcome and the next main-thread pass sweeps what it wrote. No config flag and no env bypass: every path after the plugin-root identity check exits 0 (that guard refuses with exit `2`, as it does in every hook), but a refusal that leaves an artifact un-redacted is **reported on stderr** rather than silently skipped, and a no-op write is skipped so an unchanged artifact keeps its inode. |

| `stop-chain-enforcer.sh` | Stop | `chainEnforcer` + `autopilotEnforcer` (`ZENSU_CHAIN` / `ZENSU_AUTOPILOT` env) | Hierarchical backstop. The inner TDD review chain routes first; each nudge atomically increments the integrated `stopBlockCount` field and reviewer progress resets it. Once the inner chain permits Stop, an active durable Autopilot run still blocks until `DONE`, `BLOCKED`, or `CANCELLED`; inner completion is reconciled to its exact return stage. Adopting a **deferred review** additionally consults the owner-independent working-tree occupancy check, which sees a run belonging to any session — the one place a foreign run can reach yours. That check refuses only when the hold can matter: a deferred review is actually queued in this tree, or the holder is this session's own run whose owner-keyed pointer could not be read (releasing there would infer completion for an active own generation). "Queued" tracks what the adoption itself counts as work — a marker past `pendingReviewTtlHours` is abandoned and does not sustain the refusal, an unsafe (symlinked or non-regular) marker is tamper evidence and does. With neither, the Stop is released rather than denied — before, the check ran ahead of any pending-artifact test and denied every session in a tree that merely contains, or is contained by, the holder's worktree, with a retry instruction that could not succeed while that run stayed nonterminal. A refusal has three shapes, because `--autopilot-status` is owner-scoped and cannot show a foreign run: a holder owned by another session is named together with `/zensu:autopilot-release` — the guided form, which reports the run and requires an explicit yes; the audited `zensu-log.sh --autopilot-release --run <id> --confirm` spelling goes to the operator stderr line only, never into the model-facing reason, because `--confirm` is the consent control; a holder owned by THIS session is named without any release command, deliberately, since that verb skips its self-release guard in exactly that state and would cancel the session's own live generation; and a holder that cannot be read at all names no run and prescribes no release, because ownership is unknown on that branch and the own-run case is the likely one there. `ZENSU_CHAIN=off` disables only the inner chain, while `ZENSU_AUTOPILOT=off` records audited `BLOCKED` for the outer run. Three failures to bind **release** instead of blocking: a session with no record at all and a record whose recorded project root no longer exists (neither leaves any workflow state to enforce — a deleted or recycled worktree used to wedge such a session forever with no in-session escape), plus an intact record served by a declared-incompatible plugin lineage, where the chain cannot be read from an unbound session at all and the guarantee is deferred rather than waived (`/zensu:adopt-session --confirm` re-binds it). Spawned agents always no-op. |

| `user-prompt-zen-mode.sh` | UserPromptSubmit | `zenMode`, `zenModeDefault` | zen-mode re-injection. While zen-mode resolves to active for the current session, the hook injects the mode contract as `additionalContext` on every prompt — recap line, result first, ~8 lines, depth on demand, one question and one next step per turn, a one-line chain-progress anchor carried through anything that spans several turns and placed directly above the closing next step, marked `✓` `▶` `·` `✗` and marked from an observation and never from the plan, replacing the older counter (so add no separate `Step N of M` beside it) — see [zen-mode](../skills/zen-mode/SKILL.md) the *Anchor multi-step work* rule for the full rule, which the row deliberately summarises rather than reproduces, and the never-compress carve-out for security warnings, irreversible actions, and credentials. It explicitly **overrides** any other compressed or telegraphic style mode for the duration. A skill is loaded once and fades after a handful of turns, which a low-capacity user is the least likely to notice — hence the per-prompt reminder. Resolution is three-valued, most specific first: the session marker (`${CLAUDE_PROJECT_DIR:-.}/.zensu/state/zen-mode-<scv1-session-key>.json`, holding `{"active":true\|false}`), then `hooks.zenModeDefault` (itself defaulting to `true`). A symlinked marker or state directory, and a marker that does not spell out an active mode, both resolve to OFF — unreadable state must never impose the mode on a user who may have just left it. Deactivation is performed by the HOOK, not the model: a prompt carrying `zen off` / `zen-mode off` / `turn off zen` / `stop zen`, or consisting solely of `normal mode`, records `{"active":false}` directly, so the off-switch still works after the model has drifted — and the OFF context is emitted only once the write is confirmed. ### Hook Opt-Out

Zensu ships twenty-four automatic hooks that fire across the development lifecycle (full enumeration in the [Hooks (24)](#hooks-24) table above). The configurable subset is listed below; `pre-edit-tdd-reminder.sh` has no on/off flag of its own — it is bypassed per call via the `ZENSU_TDD_GATE` env var and passes through for whole sessions frozen into vanilla mode by `tddImplementation` (see that row below), and `session-start-evidence-discipline.sh` has none by design (see [Evidence Discipline](architecture.md#evidence-discipline)). Any flagged hook can be disabled via `~/.zensu/config.json` without forking, editing, or uninstalling the plugin.

**Visible opt-outs (bypass ledger).** Env-var escapes stay free — no gate ever blocks on them — but they are no longer silent: while a TDD session is active (chain-state `active`), each gate records the escape it was bypassed through (`ZENSU_TDD_GATE`, `ZENSU_BASH_WRITE_GATE`, `ZENSU_MCP_GATE`, `ZENSU_SECRET_SCAN`, `ZENSU_CHAIN`, `ZENSU_TEST_WITNESS`, `ZENSU_EDIT_LANDING_GATE`, `ZENSU_REQUIREMENTS_GATE` — env or inline prefix) into the per-session state file, deduplicated per gate name and carrying gate names only (never command payloads or values; entries are validated against the closed eight-gate allowlist at write and read, pre-existing junk sanitized and bounded by the closed allowlist + per-name dedup). The ledger records gate escapes ONLY, so every name rendered under "Gates bypassed" is genuinely a gate that was escaped; operator interventions that are not escapes — notably the `/zensu:recover-chain` repair — record their provenance as a workflow `history` entry inside their own transaction instead of borrowing this surface. One recording semantic for every site: the escape is recorded when it short-circuits the gate's **decision point** — the witness records once per session on the first command it would otherwise have witnessed; the zensu CLI gate records when a `zensu` invocation is actually present; `ZENSU_MCP_GATE` is also honored (and therefore also recorded) by the Bash source-write gate at its own any-Bash-command decision point, so it can appear in sessions that never ran the zensu CLI; the secret-scan gate's inline escape records only on write-channel commands while its exported env escape records on the first scanned payload of any kind; `zensu-log.sh append` carries a SECOND `ZENSU_SECRET_SCAN` site with a semantic neither of those covers — it records whatever `ZENSU_SECRET_SCAN=off` reaches its OWN process environment — which includes an inline prefix written in front of the `append` command itself, since a shell assignment before a command is exported into it and the verb sees one environment either way — once per `append` invocation that takes it, and only while `ZENSU_SESSION_KEY` resolves (that verb carries no session bind of its own, so outside a Zensu-started session it records nothing); what it never records is a prefix on some OTHER command, because it does not consult the decider (R53 in `tests/structure/test-artifact-redaction.sh` is the pin, and it uses the inline spelling); inline prefixes are reported by the command parsers themselves (quoted spellings and mixed commands included; heredoc bodies, argument mentions, and channel-less commands excluded), and a command that ends up DENIED never mints a ledger entry from the denying gate — deny wins over markers WITHIN each gate (sibling hooks on the same tool call decide independently, so a gate that individually allowed may still have recorded its own escape even when another gate denied the call; over-reporting, never under-reporting). A config-disabled gate (`hooks.<flag>:false`) has no decision point — deliberate standing configuration is not ledgered. The chain-end summary surfaces the list as `Gates bypassed during this session: …` (`/zensu:autopilot` prints the build-level union into the PR body as `Gates bypassed during build: …`), sourced via `zensu-log.sh --bypass-list`, which is THREE-valued: the list; `none` — permitted only after it read a valid document that recorded no escape; or, on exit 3, an `UNREADABLE — …` line on stdout meaning the document could not be validated, which is explicitly NOT a clean ledger (a further non-zero exit, notably exit 2 for an unavailable session identity, leaves stdout empty and writes to stderr). `--bypass-note <gate>` is the write verb, itself scoped to active sessions. The ledger resets at every `--tdd-begin` and `--tdd-reset`, and BOTH echo any non-empty outgoing ledger as `previous-run bypasses (cleared now): …` so multi-run unions have a durable trace; recording is fail-open — a ledger failure never breaks the gate. **What the ledger does and does not prove.** It detects a DAMAGED document, not an authenticated deletion: `validateWorkflowState` is structural, and the `bypasses` array carries no MAC or monotone counter, so a document edited in place but left schema-valid still reads `valid` and renders `none`. Binding it would mean a new workflow-state field, which the Runtime Lineage rule makes a breaking minor — deliberately not paid for here. **This paragraph is the authoritative residual list; the skill and test surfaces point at it rather than restating it.** The releases that end a session without the chain-end report now render the line themselves, on the Stop hook's stderr — the operator channel every other release message there already uses: `ZENSU_CHAIN=off`, `hooks.chainEnforcer=false`, and the cap release after a chain fails to converge. The `--chain-done` verb renders it too, on the same channel, so the zero-change terminus discloses through either entry point — a gate escape needs no file change to be recorded. All four are silent only when the ledger is genuinely empty. What remains genuinely undisclosed is the schema-valid edited document above, and a ledger cleared by `--tdd-begin` or `--tdd-reset` — both of which echo the outgoing entries first, so the trace survives in the run log rather than in the report. Read the line as "what a readable document recorded", never as "no gate was escaped".

It is also the ONE flag read through the fail-CLOSED `zensu_hook_enabled_strict`: for every other flag "enabled" means a protection runs, so an unreadable config falling back to enabled is safe, while here "enabled" means the classifier bypass applies and the same fallback would restore a grant the user withdrew. **Its precedence is NOT the ordinary overlay** described under [Config resolution order](#config-resolution-order), and this is the one row on this page where that section does not apply: withdrawal is STICKY, so a `false` in ANY candidate file disables the grant and a project-local `.zensu/config.json` cannot re-arm one withdrawn globally; a candidate that is present but unreadable or malformed also withdraws it rather than degrading to `{}`; an EMPTY candidate list (no `ZENSU_CONFIG`, no `HOME`, no `CLAUDE_PROJECT_DIR`) withdraws it too, because then nothing was consulted at all; and only a clean `ENOENT` counts as absent, so a config the reader cannot REACH (`EACCES`, `ENOTDIR`, `ELOOP`) withdraws rather than reading as "no config here". `ZENSU_CONFIG` still replaces the pair outright, matching `cfg()`'s own contract — that is the one way a caller can present a candidate set the global file is not part of. Default `true`. |
| `reviewerSpawnPermissionCheck` | `hooks/lib/zensu-doctor-report.js` (the `/zensu:doctor` Config block, not a hook script) | When `false`, the PROACTIVE reviewer-spawn permission check does not run and its `permissions:` rows are not emitted. It exists for a user whose permissions are governed by a source that OUTRANKS `~/.claude/settings.json` — enterprise or managed settings, or a project-local `.claude/settings.local.json`, which this page documents as a real carrier of exactly this rule. For that user the exposure row is a permanent warning to edit a file that is overridden, and before this flag there was no way to silence it. **Disabling does NOT make the check silent**, deliberately: it emits one ✅ row saying it was switched off and that this is a skipped check, not an all-clear. Silence is the one verdict this check cannot qualify — removing it is the whole point of the feature — so hiding the rows under a config key would reinstate the defect. It is a BOOLEAN and never a path override: `claudeSettingsFile` refuses a `ZDOC_`/`ZENSU_` path override because an agent-writable channel could aim a check about the agent's own permissions at a file that shows a grant, and this flag suppresses the ROW without being able to redirect WHICH file is opened. Read strictly, like every other boolean here: a quoted `"false"` does NOT disable it, and the doctor's own quoted-boolean row is what tells the user why. Precedence follows the ordinary config overlay — the project config is read last and wins in BOTH directions, so a project may re-enable what a global config turned off. Default `true` (the check runs). |
| `secretScan` | `pre-write-secret-scan.sh` | When `false`, disables the secret gate — Write/Edit/MultiEdit/NotebookEdit payloads and Bash raw-write command text are no longer matched against `hooks/lib/secret-patterns.js`. While enabled (the default), a payload matching a curated rule (provider tokens, PEM headers incl. PKCS#8, high-entropy assignment) is denied with the rule name and remediation; file-tool `test(s)/`/`__tests__/`/`spec(s)/`/`testdata/`/`evals/`/`fixtures/`/`*.example.*` paths, `zensu-secret-allow` lines, and placeholders are never gated, and parser errors fail open. For a deliberate one-off use `ZENSU_SECRET_SCAN=off` (env, or inline prefix on a Bash command). Default `true`. |
| `bestSolutionFirst` | `user-prompt-best-solution-first.sh` | When `false`, suppresses **this hook's** injection on both of its legs — note it does not silence the rule outright on the main thread, where `user-prompt-zen-mode.sh`'s SCOPE clause independently carries the ranking obligation under `zenMode`; it does silence it for every spawned subagent, which zen-mode never reaches — the hook reads no rule file and injects nothing on `UserPromptSubmit` or `SubagentStart`. While enabled (the default), every prompt and every subagent spawn carries the option-quality rule: any option set put to the user must contain the best long-term / end-user solution and rank it first, with cost stated inside an option rather than used to demote or omit it. It is switchable — unlike `session-start-evidence-discipline.sh`, which has no flag by design — because it governs how a decision is presented, not whether a claim is true. Consequence worth knowing before you rely on it: the flag resolves through the normal merge, where the project-local `.zensu/config.json` wins per key, so **a repository under review can carry `bestSolutionFirst:false` and silence the directive for every subagent reviewing it**, including the `SubagentStart` leg. That is acceptable for a presentation rule and would not be for evidence discipline — which is exactly why that one reads no configuration at all. Default `true`. |
| `context.compactionNudge` | `user-prompt-context-nudge.sh` | When `false`, suppresses the UserPromptSubmit context-compaction nudge entirely — the hook reads no transcript and never proposes `/compact`. Default `true`. Lives under the top-level `context` node (not `hooks`). |
| `context.nudgeThreshold` | `user-prompt-context-nudge.sh` | Integer percent (default `50`, valid range `1..99`) of context-window occupancy at or above which the nudge fires. Out-of-range or non-integer values fall back to `50`. **Requires `context.compactionNudge:true`.** |
| `context.windowSize` | `user-prompt-context-nudge.sh` | Optional integer token budget used as the 100% denominator when computing occupancy (valid range `1000..100000000`). **Unset by default** — since hooks aren't handed the real window size, the nudge then stays silent at or below 200k occupancy (a near-full 200k session is handled by Claude Code's own auto-compaction) and treats occupancy past 200k as a proven 1M window. **Resolution rules:**

- File missing -> all hooks active (default, backward compatible)
- Key missing -> hook active
- Only an explicit boolean `false` disables a hook
- Override the config path via the `ZENSU_CONFIG` environment variable

> Flag names are **case-sensitive** and must be **JSON booleans**, not strings. A misspelled key or a quoted `"false"` is silently treated as enabled.

**Disable everything:**

```json
{
  "hooks": {
    "autoTdd": false,
    "chainEnforcer": false,
    "autopilotEnforcer": false,
    "autoFix": false,
    "pulseSession": false
  }
}
```

**Selective opt-out (e.g. silence the pulse banner only):**

```json
{
  "hooks": {
    "pulseSession": false
  }
}
```

A complete reference file with all flags enabled is included as [`config.example.json`](../config.example.json) at the repo root. Copy it to `~/.zensu/config.json` if you prefer an explicit baseline.

> **Auto-fix prerequisite:** `autoFix:true` is required for `autoFixIncludeSuggestions` and `autoFixMaxRounds` to have any effect. If `autoFix:false`, the scoped reviewer completion is still claimed exactly once and receives a ticket-bound close/self-review handoff, but no findings are changed and no auto-fix loop runs.

### Config Resolution Order

The plugin **deep-MERGES** the config files field by field to build the effective `config.json` — global as the base, the project-local file overlaid on top. Precedence, lowest to highest:

1. `$HOME/.zensu/config.json` (global base). Every key here applies unless a higher level overrides it.
2. `$CLAUDE_PROJECT_DIR/.zensu/config.json` (project-local overlay). Wins **per key** over the global file; keys it does not set **fall through** to the global value. Auto-discovered — `CLAUDE_PROJECT_DIR` is set by Claude Code for all hook subprocesses, no user setup required.
3. `$ZENSU_CONFIG` (environment override). When set, it is used **verbatim as a full override — no merge**, the explicit escape hatch for a single shell session.

A missing or malformed file is treated as `{}`, and any key absent from the merged result falls back to the hook's built-in default. So a downstream project can commit a project-local `.zensu/config.json` that sets only a few keys (e.g. enabling `autoFixIncludeSuggestions:true`) and the developer's other global settings still apply.

**One key is exempt from everything in this section: `hooks.reviewerSpawnAutoAllow`.** It is read by `zensu_hook_enabled_strict` rather than through the merged `cfg()`, because it governs a capability the plugin grants ITSELF rather than a protection it runs. There is no merge and no per-key overlay: a `false` in ANY candidate withdraws the grant, so a project-local file cannot re-arm one the user withdrew globally; a present-but-malformed candidate withdraws it instead of degrading to `{}`; and an empty candidate list withdraws it rather than falling back to the built-in default. Its row above states the full rule. Nothing else on this page behaves that way, and no other key should be given this treatment without the same argument.

> If your project commits a `.zensu/config.json` and a developer also has `~/.zensu/config.json`, the two are **merged field by field** — the project-local file wins per key, and keys it omits keep the developer's global value. Use `ZENSU_CONFIG=/path/to/other.json` to bypass the merge entirely for one session.

### Log Timestamp Style

The `/zensu:tdd` workflow writes a session log under `.zensu/logs/YYYY-MM-DD-HHMM_tdd-<slug>.log` with one line per RED/IMPL/GREEN phase. The wall-clock prefix on each line can be reformatted or suppressed via `~/.zensu/config.json`:

| Style | Inline format | Example |
|---|---|---|
| `wall` (default) | `[HH:MM:SS]` | `[14:23:45] step1 RED test_isOdd — FAIL` |
| `relative` | `[+HH:MM:SS]` from session start (< 24h); `[+Dd HH:MM:SS]` for deltas ≥ 24h | `[+00:01:23] step1 RED test_isOdd — FAIL` / `[+1d 03:45:12] step42 GREEN test_persist — PASS` |
| `none` | no prefix | `step1 RED test_isOdd — FAIL` |

Filenames retain the `YYYY-MM-DD-HHMM` session timestamp for uniqueness across multiple sessions on the same day; only the inline log-entry prefixes are affected.

Example (relative timestamps):

```json
{
  "logging": {
    "timestampStyle": "relative"
  }
}
```

Invalid values, missing keys, malformed JSON, or a missing `node` binary all fall back to `wall`.
