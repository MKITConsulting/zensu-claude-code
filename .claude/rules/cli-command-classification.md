# CLI Command Classification (`hooks/lib/zensu-mcp-tools.sh` + `hooks/lib/zensu-cli-map.sh`)

`ZENSU_AI_WORK_CAPTURE_TOOL_NAMES` is a narrow main-thread exception for
`ai-work start/submit`: they remain mutations, but report only an agreed goal
or result, also in direct mode. They cannot decide acceptance and are denied to
subagents. Mixed commands still check every other operation. The backend requires
personal CLI OAuth; no worker/shared-key identity is inferred.

_Moved from the root `CLAUDE.md`. Where this text says "this file" or names `CLAUDE.md`, it means the repository conventions as a whole: `CLAUDE.md` plus `.claude/rules/`._

The plugin drives Zensu through the typed `zensu` CLI (the MCP server still exists for the Zensu web app, but is no longer wired into the plugin). The write-gate now intercepts `zensu <noun> <verb>` Bash invocations rather than MCP tool calls.

**When the Zensu backend gains a new operation, these move together:** classify the canonical tool name in `hooks/lib/zensu-mcp-tools.sh` (state-mutating → `ZENSU_MUTATION_TOOL_NAMES`; read/telemetry → the `zensu_is_read_tool` allowlist `ZENSU_READ_TOOL_PREFIXES` / `ZENSU_READ_TOOL_NAMES`), AND map its `zensu <noun> <verb>` CLI form to that tool name in `hooks/lib/zensu-cli-map.sh`. A new command group also joins `NOUNS` in `hooks/lib/zensu-cli-words-v1.js`, its CLI alias joins `NOUN_ALIASES` there, a verb alias joins `VERB_ALIASES` there, and a verb that is itself a group joins `GROUPS` there; both gates and the marker suite read those tables, and `tests/structure/zensu-cli-words-v1.test.js` pins each of them exactly. A mutation that records a decision the person makes also joins `ZENSU_HUMAN_DECISION_TOOL_NAMES`, and a verb of the work-order protocol joins `ZENSU_WORK_ORDER_TOOL_NAMES`; either one also gets its catalog line in `agents/zensu-plm.md`, marked **person**, **worker** or **session**, and a row in `MARK_ROWS` of `tests/structure/test-zensu-plm-arg-guidance.sh`, whose C3 fails on a name without a row or a line without its mark.

**Classify by the HTTP method the CLI sends**, read from `internal/cmd/*.go` of the zensu-cli release, not by the verb's name or by what the MCP tool of the same name does. `security analyze` and `security threat-model` send the same GET of the feature's security context as `validate` and `suggest-tests`, and `doc claude-md` GETs a template, so all three are reads although their canonical names sound like writes. `pulse start|end` POST but are telemetry, and `knowledge search` POSTs a query; both stay reads. `meta scaffold-agent` sends no request and maps to nothing, so the CLI's own message reaches the agent.

**One module owns the word search: `hooks/lib/zensu-cli-words-v1.js`.** Both gates read a `zensu` call's words through it, the write gate here and the work-order gate in `hooks/lib/work-order-v1.js` (`.claude/rules/work-order-mode.md`), and neither keeps a copy, nor do the write gate's wrapper `hooks/pre-bash-zensu-gate.sh` and the dispatcher's `zensu-cli-gate` route in `hooks/lib/hook-dispatch-v1.js`, which only checks that a Bash command names `zensu` before it runs the gate body; `B53c` fails on one. `commandWords` mirrors the subcommand search of cobra v1.10.2 (`stripFlags`, `argsMinusFirstX`), which zensu-cli v0.10.0 uses: during that search the only defined flag is the persistent `--api-url`, so every `--flag` and every two-character `-f` without `=` takes the next word, an empty word is dropped, and `--` ends the search; it returns the first three remaining words. `commandNoun` answers the canonical noun of a word in `NOUNS` or `NOUN_ALIASES` and an empty string for any other word, so a first word that is no noun emits nothing. `commandVerb` applies `VERB_ALIASES`, whose one entry reads `zensu work repos` as `repositories`. `isGroup` says whether a verb, under either spelling, is itself a group: `work policy`, `work repositories` and `plan followup`. The map reads the third word only there, and a bare group maps to nothing, because cobra prints its help. The write gate emits `<noun>\t<verb>\t<third word>` with the verb read through `commandVerb`, so a new verb alias needs an entry in `VERB_ALIASES` only (`B53j`), and the marker suite reads the same table; `zensu-cli-map.sh` keeps its `work repos` arm for a caller that hands it the CLI's spelling, as `B41` does. The gate keeps only the first line of the verb and of the third word; that cut encodes its tab-separated output and is not part of the search. For a PowerShell command the gate asks `isGroup` about a group subcommand the analyzer cannot read, such as `zensu work policy $sub`, and denies it as unjudged (`B41d`), while a read whose argument is built at run time still passes (`B41e`). A word the shell expands at run time — one that carries the walker's U+0001 `DYNAMIC` marker or a `$` in the token scan — adds two readings of its invocation (`dynamicReadings`): one without the word, as an empty expansion, and one without the word and the word after it, as an expansion that ends in a value flag. The readings are extra invocations, so they can only add a deny.

**The write gate loads the module as it loads the PowerShell analyzer**: its body `hooks/checks/pre-bash-zensu-gate.sh` loads it inside the `cd -P` into the `hooks/lib` of its own installation, as `ZCW`, which stays empty when the `cd` fails, so a file in the working directory never loads (`B53i`). When the module cannot load, or loads without any one of `commandWords`, `commandNoun`, `commandVerb` and `isGroup` (`B53k`), every invocation that reaches the word search — after the inline escape, `--help` and the localhost rule — and holds a word that could name a subcommand emits an `__unreadable__` line instead of its words, and the gate denies the command with a reason of its own: it names the module and tells the main thread to reinstall the plugin, and a subagent's form reports to the main thread (`B53d`-`B53h`). `couldNameSubcommand` judges each word by its own shape, after the token scan's quotes are trimmed: a word counts unless it is empty, a flag (`-…`), a redirection (`>…`, `2>…`), a bare number or a path (it holds a `/`), and a word that holds the PowerShell analyzer's opaque value always counts. Every noun and alias passes that test (`B53m`), so the gate without the module still denies whatever the gate with it denies, and a redirection word the token scan keeps among the words, such as `2>/dev/null`, counts no more than one the shell model sets apart. Reads are denied too, because the gate can no longer tell them from a mutation, while the inline escape, `--help`, a localhost backend and a call without such a word, such as `command -v zensu >/dev/null 2>&1`, a bare `zensu`, `zensu --version 2>&1` or `zensu '' --json`, which cannot reach a subcommand, still pass (`B53f`). A flag's value and a redirection target without a `/`, such as `--title t` or `> out.log`, still count, because only the module knows which flag takes a value. The work-order gate holds the same test under the same name; each gate keeps its own copy, because the test serves exactly when the shared module is missing. The PowerShell unjudged reason does not serve here, because it sends the caller to the Bash tool, which fails the same way: the reader reason outranks it, and a PowerShell command the analyzer reports as unjudged, such as `iex '<a zensu call>'`, gets an `__unreadable__` line beside its `__unjudged__` line when the module is missing (`B53l`). The `__unreadable__` line, like `__unjudged__`, is a contract between the inline node and the shell side of the gate.

**Three subsets of the mutations pick the deny reason and one exemption:**

- `ZENSU_HUMAN_DECISION_TOOL_NAMES`: the commands zensu-cli's help calls human verbs, which need the browser login of `zensu auth login` — `work create|approve|requeue|cancel|confirm-merge|answer|overturn`, `work policy set`, `work repositories add|update|remove`, `plan push|approve|finalize|abandon|confirm-merge` and `plan followup accept|dismiss`. Their deny says that the person makes the decision and runs it and names no skill and no escape; a subagent's deny sends the decision to the main thread, and in a bound work-order session, where no person is present, the main thread's deny points to a work-order question (`zensu-work-order.sh --ask`). No skill window passes them: the gate consults the window only for the other mutations, and C3 refuses a declaration that names one. `ZENSU_MCP_GATE=off` still passes them, like every mutation.
- `ZENSU_WORK_ORDER_TOOL_NAMES`: the worker verbs `claim`, `confirm`, `release` and `usage` and the session verbs `heartbeat`, `event`, `ask` and `followup`. Their deny names the worker and the `/zensu:work` helper, and a subagent's adds that it reports the need to the main thread. No skill window passes them and the marker suite asks no window for them, because a work-order session, not a window, is their authority.
- `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES`: `ask` and `followup`, the mutations among the verbs that `SESSION_WORK_VERBS` in `hooks/lib/work-order-v1.js` lets through. When `zensu_work_order_hook bound` answers `bound` — the session token, this session's marker and its binding, the same test that wakes the work-order hooks, answered by the side-effect-free `bound` verb of `work-order-v1.js` — the write-gate leaves them to `pre-work-order-gate.sh`. A subagent never gets the exemption.

When one command holds several denied invocations, the gate keeps reading them and picks the reason from a human decision first, then a work-order verb, then the first denied tool, so a decision chained after an ordinary mutation never gets the generic reason with its escape hint.

`zensu-mcp-tools.sh` is the single source of truth for read/mutation classification, consumed by:

- `hooks/pre-bash-zensu-gate.sh`, with its body `hooks/checks/pre-bash-zensu-gate.sh` — the PreToolUse(Bash) write-gate: parses `zensu <noun> <verb>` from the command through `commandInvocations` in `hooks/lib/subagent-shell-guard-v1.js` and through its own token scan, gating what either finds (the token scan alone when that module cannot load), and for a PowerShell payload through `zensuInvocations` in `hooks/lib/powershell-command-v1.js` instead, which reports a call it cannot read as unjudged and denies it; it reads each call's words through `hooks/lib/zensu-cli-words-v1.js`, resolves them via `zensu-cli-map.sh`, and classifies via this SoT — `zensu_is_read_tool` commands pass ungated, mutations are default-denied unless workflow-driven.
- `hooks/lib/zensu-cli-map.sh` — the CLI→tool-name adapter the gate and the marker test use. Its mutation entries stay a subset of `ZENSU_MUTATION_TOOL_NAMES`.
- `tests/structure/test-skill-workflow-markers.sh` — the build-time guard that fails if a skill runs a `zensu` mutation command (resolved via the map, third word included) without the `--workflow-begin` / `--workflow-end` markers, or runs one its window does not declare.

Consequences of forgetting a new operation:

- **New mutation, not added to `ZENSU_MUTATION_TOOL_NAMES`:** the marker test will NOT flag a skill that runs it un-wrapped, and C2 fails because the map emits an unclassified name. **Test-coverage gap, not an open gate.**
- **New read, not added to the read-allowlist:** if the map resolves it to a name that classifies as a mutation, it is wrongly gated on the main thread until added.
- **New CLI verb, not added to `zensu-cli-map.sh`:** the gate cannot resolve it → treated as unknown/neutral → allowed ungated, so a mutating verb would slip the nudge. Add every new mutating verb to the map.
- **New command group, not added to `NOUNS` in `hooks/lib/zensu-cli-words-v1.js`:** the write gate never emits it, so none of its verbs reaches the map and every mutation in the group passes ungated.

Invariants, pinned in `tests/structure/test-skill-workflow-markers.sh`: no mutation classifies as a read, because the gate checks reads first; the human-decision and work-order names are mutations, the session names are work-order names and the two families are disjoint (C1); every tool the map emits is classified (C2); every `--workflow-begin --tools` declaration names mutations only and never a human decision or a work-order verb, so `ZENSU_MUTATION_TOOL_NAMES` stays a superset of every declaration (C3); every CLI mutation a skill with a window runs is declared in that window, a human decision or a work-order verb excepted, because a skill tells the person to run the one and leaves the other to the work-order session (C4, I5-human, I5-order); the session names are exactly the mutations among `SESSION_WORK_VERBS` (C5); the plan verbs whose tools are human decisions are exactly the work-order gate's exported `HUMAN_PLAN_VERBS` (C6). `tests/structure/test-bash-zensu-gate.sh` pins the tool and class of every v0.10.0 work, plan, mocks, design and journeys-step verb (B41) and the hook's decisions for them (B42-B47).

**Coupled sites.** `zensu_work_order_hook bound` in `hooks/lib/zensu-work-order-hook.sh` and the `bound` verb of `hooks/lib/work-order-v1.js`; the exported `SESSION_WORK_VERBS` and `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES` (C5); the deny texts and B19, B19b, B37, B37b, B43a-B43e, B46f, B53d-B53h and B53l; the word reader `hooks/lib/zensu-cli-words-v1.js` with its unit file, `B53a`-`B53c` and `B53i`-`B53k`, its `ZCW` load beside `ZPS`, `CLI_VERB_ALIASES` in `tests/structure/test-skill-workflow-markers.sh`, the work-order gate's `reader` finding, and `couldNameSubcommand`, copied in the gate body and in `hooks/lib/work-order-v1.js`; the catalog marks of `agents/zensu-plm.md` and C3 of `tests/structure/test-zensu-plm-arg-guidance.sh`; docs/gates.md §"CLI Write-Gate", the `pre-bash-zensu-gate.sh` and `mcpGate` rows of `docs/configuration.md`, docs/work-order-mode.md §"The tool hooks" and §"Work-order hooks" of `skills/work/references/protocol.md`.

**Known gaps, accepted and named:**

- `--help` or `-h` anywhere counts as help, also where it is the value of a flag (`--title --help`), which cobra hands to the flag before it runs the command.
- The token scan reads raw words with their quotes, so a quoted noun or verb is judged only by the shell-model reading.
- The extra readings of an expanded word assume it holds flags and their values. An expansion that supplies the noun or the verb itself (`zensu features "$VERB"`) stays unjudged.
- The classification follows zensu-cli v0.10.0. A verb a later release adds stays unmapped, and passes, until the map learns it.

**Version: `minor`.** The gate now denies the work, plan, mocks and journeys-step mutations, the flag-value, empty-word and expanded-word spellings that hid a mutation, and a human decision or work-order verb inside a window that declares it, which changes the capability set of every session a newer installation would serve (`.claude/rules/runtime-lineage.md`). It also denies less: three reads and the `meta scaffold-agent` stub now pass. Moving the word search into `hooks/lib/zensu-cli-words-v1.js` is a `patch` on its own: an intact installation denies exactly what it denied before, and only an installation without the module denies more.
