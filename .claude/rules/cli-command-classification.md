# CLI Command Classification (`hooks/lib/zensu-mcp-tools.sh` + `hooks/lib/zensu-cli-map.sh`)

_Moved from the root `CLAUDE.md`. Where this text says "this file" or names `CLAUDE.md`, it means the repository conventions as a whole: `CLAUDE.md` plus `.claude/rules/`._

The plugin drives Zensu through the typed `zensu` CLI (the MCP server still exists for the Zensu web app, but is no longer wired into the plugin). The write-gate now intercepts `zensu <noun> <verb>` Bash invocations rather than MCP tool calls.

**When the Zensu backend gains a new operation, these move together:** classify the canonical tool name in `hooks/lib/zensu-mcp-tools.sh` (state-mutating → `ZENSU_MUTATION_TOOL_NAMES`; read/telemetry → the `zensu_is_read_tool` allowlist `ZENSU_READ_TOOL_PREFIXES` / `ZENSU_READ_TOOL_NAMES`), AND map its `zensu <noun> <verb>` CLI form to that tool name in `hooks/lib/zensu-cli-map.sh`. A new command group also joins the parser's `NOUNS` set in `hooks/pre-bash-zensu-gate.sh`, its CLI alias joins `ALIAS` there, a verb that is itself a group joins `GROUPS` there, and the alias `case` in `tests/structure/test-skill-workflow-markers.sh` mirrors `ALIAS`. A mutation that records a decision the person makes also joins `ZENSU_HUMAN_DECISION_TOOL_NAMES`, and a verb of the work-order protocol joins `ZENSU_WORK_ORDER_TOOL_NAMES`; either one also gets its catalog line in `agents/zensu-plm.md`, marked **person**, **worker** or **session**, and a row in `MARK_ROWS` of `tests/structure/test-zensu-plm-arg-guidance.sh`, whose C3 fails on a name without a row or a line without its mark.

**Classify by the HTTP method the CLI sends**, read from `internal/cmd/*.go` of the zensu-cli release, not by the verb's name or by what the MCP tool of the same name does. `security analyze` and `security threat-model` send the same GET of the feature's security context as `validate` and `suggest-tests`, and `doc claude-md` GETs a template, so all three are reads although their canonical names sound like writes. `pulse start|end` POST but are telemetry, and `knowledge search` POSTs a query; both stay reads. `meta scaffold-agent` sends no request and maps to nothing, so the CLI's own message reaches the agent.

**How the parser finds the command.** It mirrors the subcommand search of cobra v1.10.2 (`stripFlags`, `argsMinusFirstX`), which zensu-cli v0.10.0 uses: during that search the only defined flag is the persistent `--api-url`, so every `--flag` and every two-character `-f` without `=` takes the next word, an empty word is dropped, and `--` ends the search. The first remaining word must be in `NOUNS`, normalized through `ALIAS`, and the parser emits `<noun>\t<verb>\t<third word>`, keeping only the first line of each word. The map reads the third word only where the verb is itself a group: `work policy`, `work repositories` (CLI alias `repos`) and `plan followup`. `zensuCommandWords` in `hooks/lib/work-order-v1.js` mirrors the same search for the work-order gate, and the two move together. A bare group maps to nothing, because cobra prints its help. For a PowerShell command the gate's `GROUPS` set names the same three groups, so a group subcommand the analyzer cannot read, such as `zensu work policy $sub`, is denied as unjudged (`B41d`), while a read whose argument is built at run time still passes (`B41e`). A word the shell expands at run time — one that carries the walker's U+0001 `DYNAMIC` marker or a `$` in the token scan — adds two readings of its invocation (`dynamicReadings`): one without the word, as an empty expansion, and one without the word and the word after it, as an expansion that ends in a value flag. The readings are extra invocations, so they can only add a deny.

**Three subsets of the mutations pick the deny reason and one exemption:**

- `ZENSU_HUMAN_DECISION_TOOL_NAMES`: the commands zensu-cli's help calls human verbs, which need the browser login of `zensu auth login` — `work create|approve|requeue|cancel|confirm-merge|answer|overturn`, `work policy set`, `work repositories add|update|remove`, `plan push|approve|finalize|abandon|confirm-merge` and `plan followup accept|dismiss`. Their deny says that the person makes the decision and runs it and names no skill and no escape; a subagent's deny sends the decision to the main thread, and in a bound work-order session, where no person is present, the main thread's deny points to a work-order question (`zensu-work-order.sh --ask`). No skill window passes them: the gate consults the window only for the other mutations, and C3 refuses a declaration that names one. `ZENSU_MCP_GATE=off` still passes them, like every mutation.
- `ZENSU_WORK_ORDER_TOOL_NAMES`: the worker verbs `claim`, `confirm`, `release` and `usage` and the session verbs `heartbeat`, `event`, `ask` and `followup`. Their deny names the worker and the `/zensu:work` helper, and a subagent's adds that it reports the need to the main thread. No skill window passes them and the marker suite asks no window for them, because a work-order session, not a window, is their authority.
- `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES`: `ask` and `followup`, the mutations among the verbs that `SESSION_WORK_VERBS` in `hooks/lib/work-order-v1.js` lets through. When `zensu_work_order_hook bound` answers `bound` — the session token, this session's marker and its binding, the same test that wakes the work-order hooks, answered by the side-effect-free `bound` verb of `work-order-v1.js` — the write-gate leaves them to `pre-work-order-gate.sh`. A subagent never gets the exemption.

When one command holds several denied invocations, the gate keeps reading them and picks the reason from a human decision first, then a work-order verb, then the first denied tool, so a decision chained after an ordinary mutation never gets the generic reason with its escape hint.

`zensu-mcp-tools.sh` is the single source of truth for read/mutation classification, consumed by:

- `hooks/pre-bash-zensu-gate.sh` — the PreToolUse(Bash) write-gate: parses `zensu <noun> <verb>` from the command through `commandInvocations` in `hooks/lib/subagent-shell-guard-v1.js` and through its own token scan, gating what either finds (the token scan alone when that module cannot load), and for a PowerShell payload through `zensuInvocations` in `hooks/lib/powershell-command-v1.js` instead, which reports a call it cannot read as unjudged and denies it; it resolves each via `zensu-cli-map.sh`, and classifies via this SoT — `zensu_is_read_tool` commands pass ungated, mutations are default-denied unless workflow-driven.
- `hooks/lib/zensu-cli-map.sh` — the CLI→tool-name adapter the gate and the marker test use. Its mutation entries stay a subset of `ZENSU_MUTATION_TOOL_NAMES`.
- `tests/structure/test-skill-workflow-markers.sh` — the build-time guard that fails if a skill runs a `zensu` mutation command (resolved via the map, third word included) without the `--workflow-begin` / `--workflow-end` markers, or runs one its window does not declare.

Consequences of forgetting a new operation:

- **New mutation, not added to `ZENSU_MUTATION_TOOL_NAMES`:** the marker test will NOT flag a skill that runs it un-wrapped, and C2 fails because the map emits an unclassified name. **Test-coverage gap, not an open gate.**
- **New read, not added to the read-allowlist:** if the map resolves it to a name that classifies as a mutation, it is wrongly gated on the main thread until added.
- **New CLI verb, not added to `zensu-cli-map.sh`:** the gate cannot resolve it → treated as unknown/neutral → allowed ungated, so a mutating verb would slip the nudge. Add every new mutating verb to the map.
- **New command group, not added to `NOUNS`:** the parser never emits it, so none of its verbs reaches the map and every mutation in the group passes ungated.

Invariants, pinned in `tests/structure/test-skill-workflow-markers.sh`: no mutation classifies as a read, because the gate checks reads first; the human-decision and work-order names are mutations, the session names are work-order names and the two families are disjoint (C1); every tool the map emits is classified (C2); every `--workflow-begin --tools` declaration names mutations only and never a human decision or a work-order verb, so `ZENSU_MUTATION_TOOL_NAMES` stays a superset of every declaration (C3); every CLI mutation a skill with a window runs is declared in that window, a human decision or a work-order verb excepted, because a skill tells the person to run the one and leaves the other to the work-order session (C4, I5-human, I5-order); the session names are exactly the mutations among `SESSION_WORK_VERBS` (C5); the plan verbs whose tools are human decisions are exactly the work-order gate's exported `HUMAN_PLAN_VERBS` (C6). `tests/structure/test-bash-zensu-gate.sh` pins the tool and class of every v0.10.0 work, plan, mocks, design and journeys-step verb (B41) and the hook's decisions for them (B42-B47).

**Coupled sites.** `zensu_work_order_hook bound` in `hooks/lib/zensu-work-order-hook.sh` and the `bound` verb of `hooks/lib/work-order-v1.js`; the exported `SESSION_WORK_VERBS` and `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES` (C5); the deny texts and B19, B19b, B37, B37b, B43a-B43e and B46f; the catalog marks of `agents/zensu-plm.md` and C3 of `tests/structure/test-zensu-plm-arg-guidance.sh`; docs/gates.md §"CLI Write-Gate", the `pre-bash-zensu-gate.sh` and `mcpGate` rows of `docs/configuration.md`, docs/work-order-mode.md §"The tool hooks" and §"Work-order hooks" of `skills/work/references/protocol.md`.

**Known gaps, accepted and named:**

- `--help` or `-h` anywhere counts as help, also where it is the value of a flag (`--title --help`), which cobra hands to the flag before it runs the command.
- The localhost reading of the two-word `--api-url` and of `ZENSU_API_URL` can take a call to a remote backend for a local one. It reads the two-word flag also where it is another flag's value (`--title --api-url …`), at its first occurrence although pflag lets a later one win, after a `--`, in the raw fragments of a call only the token scan finds (inside an `ssh` or `su -c` string), and where a word built at run time, a glob or `xargs` can add a later `--api-url=` that wins. When the one-word spelling does not count, `ZENSU_API_URL` decides although the CLI's flag overrides it. `isLocalUrl` ends the host at the first `:` or `/`, so `http://localhost:8090@api.zensu.dev`, whose host a URL parser reads as `api.zensu.dev`, counts as local. In PowerShell a word built at run time adds no extra reading, so a `--help`, `-h` or two-word `--api-url` right after it is not read as its value. Closing any of these denies calls the released gate allows, which is a `minor` change.
- The one-word `--api-url=` counts only in a call the shell model reads in full (`oneWordLocal` and `oneWordTrusted` in `hooks/pre-bash-zensu-gate.sh`). Every `--api-url=` word must name a plain local URL (`PLAIN_LOCAL_URL`), stand ahead of any `--` and follow no word that starts with `-` and holds no `=`. The shell-model and PowerShell readings are judged on their words as the CLI receives them, quote characters included, and only the token scan's raw words are unquoted; the readings `dynamicReadings` derives never relax. The command must hold no `$` or backtick, because an expansion can rewrite the call (a function that forwards `"$@"`, an ANSI-C or locale string that spells the name) and the walker visits a substitution in a shell-read heredoc twice; no brace, because the walker expands only comma groups and stops at `MAX_BRACE_WORDS`; no carriage return, because the walker joins a backslash before CR LF as a line continuation and bash does not; no glob character; no `xargs`, which appends words from its input, and no `watch`, which re-parses its words through `sh -c`; and on Windows no backslash, which the parse turns into `/` there. Last, the walker must find as many `zensu` calls as the command text holds `zensu` words once line continuations, backslashes and quote characters are removed, in any letter case, so an escaped, quoted or uppercase name it finds cannot offset a call only the token scan sees. The released gate never read this spelling, so each condition only narrows the relaxation. A local call that misses one stays denied, such as one with the flag right after a boolean flag (`--json --api-url=…`), any `$`, a `?` or brace in a title, a JSON argument, a Windows path, or `zensu`, `xargs` or `watch` in a title.
- The token scan reads raw words with their quotes, so a quoted noun or verb is judged only by the shell-model reading.
- The extra readings of an expanded word assume it holds flags and their values. An expansion that supplies the noun or the verb itself (`zensu features "$VERB"`) stays unjudged.
- The classification follows zensu-cli v0.10.0. A verb a later release adds stays unmapped, and passes, until the map learns it.

**Version: `minor`.** The gate now denies the work, plan, mocks and journeys-step mutations, the flag-value, empty-word and expanded-word spellings that hid a mutation, and a human decision or work-order verb inside a window that declares it, which changes the capability set of every session a newer installation would serve (`.claude/rules/runtime-lineage.md`). It also denies less: three reads and the `meta scaffold-agent` stub now pass.
