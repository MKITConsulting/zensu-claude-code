# CLI Command Classification (`hooks/lib/zensu-mcp-tools.sh` + `hooks/lib/zensu-cli-map.sh`)

`ZENSU_AI_WORK_CAPTURE_TOOL_NAMES` is a narrow main-thread exception for
`ai-work start/submit`: they remain mutations, but report only an agreed goal
or result, also in direct mode. They cannot decide acceptance and are denied to
subagents. Mixed commands still check every other operation. The backend requires
personal CLI OAuth; no worker/shared-key identity is inferred.

_Moved from the root `CLAUDE.md`. Where this text says "this file" or names `CLAUDE.md`, it means the repository conventions as a whole: `CLAUDE.md` plus `.claude/rules/`._

The plugin drives Zensu through the typed `zensu` CLI (the MCP server still exists for the Zensu web app, but is no longer wired into the plugin). The write-gate now intercepts `zensu <noun> <verb>` Bash invocations rather than MCP tool calls.

**When the Zensu backend gains a new operation, these move together:** classify the canonical tool name in `hooks/lib/zensu-mcp-tools.sh` (state-mutating → `ZENSU_MUTATION_TOOL_NAMES`; read/telemetry → the `zensu_is_read_tool` allowlist `ZENSU_READ_TOOL_PREFIXES` / `ZENSU_READ_TOOL_NAMES`), AND map its `zensu <noun> <verb>` CLI form to that tool name in `hooks/lib/zensu-cli-map.sh`. A new command group also joins the parser's `NOUNS` set in `hooks/pre-bash-zensu-gate.sh`, its CLI alias joins `ALIAS` there, a verb that is itself a group joins `GROUPS` there, and the alias `case` in `tests/structure/test-skill-workflow-markers.sh` mirrors `ALIAS`. A mutation that records a decision the person makes also joins `ZENSU_HUMAN_DECISION_TOOL_NAMES`, and a verb of the work-order protocol joins `ZENSU_WORK_ORDER_TOOL_NAMES`; either one also gets its catalog line in `agents/zensu-plm.md`, marked **person**, **worker** or **session**, and a row in `MARK_ROWS` of `tests/structure/test-zensu-plm-arg-guidance.sh`, whose C3 fails on a name without a row or a line without its mark.

**Classify by the HTTP method the CLI sends**, read from `internal/cmd/*.go` of the zensu-cli release, not by the verb's name or by what the MCP tool of the same name does. `security analyze` and `security threat-model` send the same GET of the feature's security context as `validate` and `suggest-tests`, and `doc claude-md` GETs a template, so all three are reads although their canonical names sound like writes. `pulse start|end` POST but are telemetry, and `knowledge search` POSTs a query; both stay reads. `meta scaffold-agent` sends no request and maps to nothing, so the CLI's own message reaches the agent.

**How the gate finds the CLI name.** macOS (APFS by default) and Windows resolve a command name case-insensitively, with Unicode's case fold (APFS resolves the long s `ſ` as `s`, measured on macOS), and Windows adds `.exe` and backslash paths, so `ZENSU`, `zenſu`, `Zensu.exe`, `/opt/homebrew/bin/ZENSU` and `'C:\tools\zensu.exe'` run the CLI there. Both Bash readings therefore take the name as such a file system resolves it, on every platform. The inline script first joins every line continuation the way the shell does (`joined` consumes backslash pairs left to right, so an escaped backslash before a line break ends the line: B55v, B35x11, B56e), and `plain` is `joined` with the `$` in front of a quote, then every quote and backslash removed. It exits early only when none of four texts names a `zensu` word in any letter case (`NAMED`, flags `iu`, `candidates`): the command text, because removing the backslashes of a quoted Windows path (`"C:\Program Files\Zensu\zensu.exe"`) joins the name to the folder before it (B56b); `plain`; the command text with only the `$`, quotes and backslashes removed; and `plain` built after comments are cut, because a comment ends at its line break even after a backslash (B55v2, B55v3). The token scan splits `joined`, drops the `$` in front of a quote and every quote and backslash from the command word, folds it with `toUpperCase().toLowerCase()` before it matches `WRAP`, and strips a `.exe` from the basename (B39e, B39f, B55w to B55y2). The walker asks `commandInvocations` in `hooks/lib/subagent-shell-guard-v1.js` for the host platform's reading with `foldNames: true`, and on win32 also for the `linux` reading, which keeps `\--api-url` and `\--` (B52b, B56d): `foldNames` folds every command name with the same Unicode fold in `commandName`, so `ENV`, `XARGS`, `EVAL` and `BASH -c` unwrap on Linux too (B56c, B35q2, B35q3, B35x9), and on win32 `commandName` cuts a word at its last `/` or `\`; on a win32 host the gate also cuts each walker name at its last `\`, so the POSIX reading of a path with an escaped letter (`C:\\Zensu\\z\ensu.exe`) counts too (B56b). Every platform rather than only those two: the gate cannot know the file system of each `PATH` directory, a false deny on a case-sensitive Linux file system needs a distinct `ZENSU` program, and the PowerShell reading already matches any letter case. In a Bash call nouns and verbs stay case-sensitive, because zensu-cli v0.10.0 enables neither cobra's `EnableCaseInsensitive` nor prefix matching, so `ZENSU SECURITY CLASSIFY f1` fails in the CLI and is not read as a mutation (B55r). The PowerShell reading lowercases the words after the name (`rest`), so it denies `ZENSU Security Classify f1` (B40c). The token scan cannot tell an `ssh` string from a commit message, so folding its command word also reads prose after a separator inside a quoted string, such as `git commit -m "x; Zensu features create y"`, as a call (B55u); that widens the heredoc and search-pattern false positive the lowercase name already had, and it is kept because B55l needs the fold. When the walker finds no call and the token scan finds one, the inline script adds a `__textonly__` line, and the deny reason then names the file remedy (`git commit -F`, `gh pr create --body-file`), because an inline prefix in front of the command cannot reach a call inside quoted text (B55u2). The shell side keeps the node child's exit status (`PARSE_STATUS`) and denies a command whose parse failed instead of letting it through unread (B39g); the derived readings join through `flatMap`, because spreading every invocation into one call threw at about 100000 calls under the payload limit (B48i).

**How the parser finds the command.** It mirrors the subcommand search of cobra v1.10.2 (`stripFlags`, `argsMinusFirstX`), which zensu-cli v0.10.0 uses: during that search the only defined flag is the persistent `--api-url`, so every `--flag` and every two-character `-f` without `=` takes the next word, an empty word is dropped, and `--` ends the search. The first remaining word must be in `NOUNS`, normalized through `ALIAS`, and the parser emits `<noun>\t<verb>\t<third word>`, keeping only the first line of each word. The map reads the third word only where the verb is itself a group: `work policy`, `work repositories` (CLI alias `repos`) and `plan followup`. `zensuCommandWords` in `hooks/lib/work-order-v1.js` mirrors the same search for the work-order gate, and the two move together. A bare group maps to nothing, because cobra prints its help. For a PowerShell command the gate's `GROUPS` set names the same three groups, so a group subcommand the analyzer cannot read, such as `zensu work policy $sub`, is denied as unjudged (`B41d`), while a read whose argument is built at run time still passes (`B41e`). A word the shell expands at run time — one that carries the walker's U+0001 `DYNAMIC` marker or a `$` in the token scan — adds two readings of its invocation (`dynamicReadings`): one without the word, as an empty expansion, and one without the word and the word after it, as an expansion that ends in a value flag. The readings are extra invocations, so they can only add a deny.

**How the gate reads the backend.** `backendLocal` in `hooks/pre-bash-zensu-gate.sh` follows pflag, which parses zensu-cli's flags: every `--api-url` occurrence counts in either spelling and the CLI takes the last one, so the call is local only when every occurrence names a local backend, and a remote occurrence followed by a local one stays denied. An occurrence is certain to be the flag only ahead of the first `--` and of the first word built at run time (`runTime`: the walker's U+0001 marker, a `$` in the token scan, PowerShell's `OPAQUE_ARGUMENT`), and not right after a word that starts with `-` and holds no `=`, because such a word may take it as its value, a `--` may itself be a value, and a word built at run time may expand to `--`. When no occurrence is certain, the CLI may fall back to `ZENSU_API_URL`, which must then name a local backend too; with no occurrence it decides alone. An inline assignment decides even when empty, because it replaces the variable for that call, but an inline `ZENSU_API_URL+=` appends and is never local (`envAppended`). Else the hook's own environment (`ZAPI`) decides, but only while the command does not name `ZENSU_API_URL` at all (`envNamed`, read after line continuations, backslashes, quotes and backticks are removed, and in PowerShell also over the analyzer's `spellings()`), because the shell model records no environment change outside the call's own prefix: an earlier assignment, `export`, `declare -x`, `read`, `printf -v`, `unset`, `env -u` or a PowerShell `$env:` write all go unread. A two-word occurrence needs a following word. The gate carries no table of zensu-cli's boolean flags, which would tie it to one CLI release, so a local flag right after a boolean flag (`--json --api-url …`) is denied unless `ZENSU_API_URL` is local. `isLocalUrl` takes a value only when it spells `localhost`, `127.0.0.1`, `0.0.0.0` or `[::1]` right after an optional `http://` or `https://` (`LOCAL_START`), holds only printable ASCII without a backslash, and node's URL parser confirms that host with no user name or password: the spelling keeps out what only the parser normalizes to a loopback host (`127.1`, `2130706433`, `local%68ost`), and the parser keeps out what a prefix match misreads (`http://localhost:8090@api.zensu.dev`). It cuts a value at its first run-time part (U+0001, NUL or `$`) and keeps the value only when the literal text before the cut already ends the host with `/`, `?` or `#`, so `"http://localhost:8090/$PREFIX"` stays local while a run-time port (`localhost:$PORT`, which may expand to `8090@api.zensu.dev`) does not. The token scan's raw tokens become shell words first (`shellWords`: quote state carries across tokens, and a token that starts with `#` outside a word ends the words), so a quoted title cannot add an occurrence, a `--` or a dash word, and a quote-glued fragment cannot become an occurrence. On Windows the walker turns an unquoted backslash before a word character into `/`, so the gate adds a second walker reading for the POSIX platform, in which `\--api-url` and `\--` keep their meaning. A PowerShell call that holds a word built at run time is not local while the command holds `--%` or more `--api-url` text than its calls' words hold (`psHidden`), because the analyzer turns such a flag into `OPAQUE_ARGUMENT`. The one-word spelling is local only in a call the gate reads in full (below); in any other call it is not local, whatever `ZENSU_API_URL` says, because the flag overrides the variable.

**Three subsets of the mutations pick the deny reason and one exemption:**

- `ZENSU_HUMAN_DECISION_TOOL_NAMES`: the commands zensu-cli's help calls human verbs, which need the browser login of `zensu auth login` — `work create|approve|requeue|cancel|confirm-merge|answer|overturn`, `work policy set`, `work repositories add|update|remove`, `plan push|approve|finalize|abandon|confirm-merge` and `plan followup accept|dismiss`. Their deny says that the person makes the decision and runs it and names no skill and no escape; a subagent's deny sends the decision to the main thread, and in a bound work-order session, where no person is present, the main thread's deny points to a work-order question (`zensu-work-order.sh --ask`). No skill window passes them: the gate consults the window only for the other mutations, and C3 refuses a declaration that names one. `ZENSU_MCP_GATE=off` still passes them, like every mutation.
- `ZENSU_WORK_ORDER_TOOL_NAMES`: the worker verbs `claim`, `confirm`, `release` and `usage` and the session verbs `heartbeat`, `event`, `ask` and `followup`. Their deny names the worker and the `/zensu:work` helper, and a subagent's adds that it reports the need to the main thread. No skill window passes them and the marker suite asks no window for them, because a work-order session, not a window, is their authority.
- `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES`: `ask` and `followup`, the mutations among the verbs that `SESSION_WORK_VERBS` in `hooks/lib/work-order-v1.js` lets through. When `zensu_work_order_hook bound` answers `bound` — the session token, this session's marker and its binding, the same test that wakes the work-order hooks, answered by the side-effect-free `bound` verb of `work-order-v1.js` — the write-gate leaves them to `pre-work-order-gate.sh`. A subagent never gets the exemption. That gate reads the CLI name only as `zensu`, in lowercase and without `.exe` (`commandName` in `hooks/lib/work-order-v1.js`), so in a bound session on macOS and Windows an `ask` or `followup` spelled another way gets this exemption without that gate's checks, its token-host deny included, until that gate reads the name the way this one does.

When one command holds several denied invocations, the gate keeps reading them and picks the reason from a human decision first, then a work-order verb, then the first denied tool, so a decision chained after an ordinary mutation never gets the generic reason with its escape hint.

`zensu-mcp-tools.sh` is the single source of truth for read/mutation classification, consumed by:

- `hooks/pre-bash-zensu-gate.sh`, with its body `hooks/checks/pre-bash-zensu-gate.sh` — the PreToolUse(Bash) write-gate: parses `zensu <noun> <verb>` from the command through `commandInvocations` in `hooks/lib/subagent-shell-guard-v1.js` and through its own token scan, gating what either finds (the token scan alone when that module cannot load), and for a PowerShell payload through `zensuInvocations` in `hooks/lib/powershell-command-v1.js` instead, which reports a call it cannot read as unjudged and denies it; it resolves each via `zensu-cli-map.sh`, and classifies via this SoT — `zensu_is_read_tool` commands pass ungated, mutations are default-denied unless workflow-driven.
- `hooks/lib/zensu-cli-map.sh` — the CLI→tool-name adapter the gate and the marker test use. Its mutation entries stay a subset of `ZENSU_MUTATION_TOOL_NAMES`.
- `tests/structure/test-skill-workflow-markers.sh` — the build-time guard that fails if a skill runs a `zensu` mutation command (resolved via the map, third word included) without the `--workflow-begin` / `--workflow-end` markers, or runs one its window does not declare.

Consequences of forgetting a new operation:

- **New mutation, not added to `ZENSU_MUTATION_TOOL_NAMES`:** the marker test will NOT flag a skill that runs it un-wrapped, and C2 fails because the map emits an unclassified name. **Test-coverage gap, not an open gate.**
- **New read, not added to the read-allowlist:** if the map resolves it to a name that classifies as a mutation, it is wrongly gated on the main thread until added.
- **New CLI verb, not added to `zensu-cli-map.sh`:** the gate cannot resolve it → treated as unknown/neutral → allowed ungated, so a mutating verb would slip the nudge. Add every new mutating verb to the map.
- **New command group, not added to `NOUNS`:** the parser never emits it, so none of its verbs reaches the map and every mutation in the group passes ungated.

Invariants, pinned in `tests/structure/test-skill-workflow-markers.sh`: no mutation classifies as a read, because the gate checks reads first; the human-decision and work-order names are mutations, the session names are work-order names and the two families are disjoint (C1); every tool the map emits is classified (C2); every `--workflow-begin --tools` declaration names mutations only and never a human decision or a work-order verb, so `ZENSU_MUTATION_TOOL_NAMES` stays a superset of every declaration (C3); every CLI mutation a skill with a window runs is declared in that window, a human decision or a work-order verb excepted, because a skill tells the person to run the one and leaves the other to the work-order session (C4, I5-human, I5-order); the session names are exactly the mutations among `SESSION_WORK_VERBS` (C5); the plan verbs whose tools are human decisions are exactly the work-order gate's exported `HUMAN_PLAN_VERBS` (C6). `tests/structure/test-bash-zensu-gate.sh` pins the tool and class of every v0.10.0 work, plan, mocks, design and journeys-step verb (B41) and the hook's decisions for them (B42-B47).

**Coupled sites.** `zensu_work_order_hook bound` in `hooks/lib/zensu-work-order-hook.sh` and the `bound` verb of `hooks/lib/work-order-v1.js`; the exported `SESSION_WORK_VERBS` and `ZENSU_WORK_ORDER_SESSION_TOOL_NAMES` (C5); the deny texts and B19, B19b, B37, B37b, B43a-B43e and B46f; the name reading and B55a-B55z, B56-B56e, B39e-B39g, B48h, B48i, B35q2, B35q3 and B35x9-B35x11, the `foldNames` and win32 assertions of the walker test in `tests/structure/subagent-shell-guard-v1.test.js`, the `__textonly__` line between the inline script and the shell side, the PowerShell `rest` fold and B40c; the catalog marks of `agents/zensu-plm.md` and C3 of `tests/structure/test-zensu-plm-arg-guidance.sh`; docs/gates.md §"CLI Write-Gate", the `pre-bash-zensu-gate.sh` and `mcpGate` rows of `docs/configuration.md`, docs/work-order-mode.md §"The tool hooks" and §"Work-order hooks" of `skills/work/references/protocol.md`.

**Known gaps, accepted and named:**

- `--help` or `-h` anywhere counts as help, also where it is the value of a flag (`--title --help`), which cobra hands to the flag before it runs the command.
- The localhost reading of the two-word `--api-url` and of `ZENSU_API_URL` can still take a call to a remote backend for a local one where a word the gate does not read as an occurrence becomes one: a word built at run time after the last occurrence or anywhere in a call without one, a glob, an unexpanded brace word (`--api-ur{l..l}`: the walker expands only comma groups up to `MAX_BRACE_WORDS`, the token scan none) or `xargs` can add a later occurrence that wins (`zensu --api-url http://localhost:8090 features create … $X`), and `watch` re-parses its words through `sh -c`, so an escaped `"\\--api-url=…"` becomes one there. A call only the token scan finds, inside an `ssh`, `su -c`, `docker … exec` or `kubectl exec` string, is read on the words that string spells, although the remote shell runs it with its own environment and `localhost` there names the remote host or container, which for a self-hosted deployment is the tracked product; the durable fix, never relaxing a call outside the shell model, would deny every such call. An `env -u` or `env -i` behind an inline assignment (the walker keeps the assignment), an `env -i` or a `sudo` that resets the environment, a file the command sources and a variable name the shell assembles at run time (`ZENSU_API$()_URL`) are not read, so the inline assignment or the hook's own value still decides. In PowerShell a word built at run time adds no extra reading, so a `--help` or `-h` right after it is not read as its value. Closing the first gap would deny every local call that carries an expansion, such as a quoted `"$TITLE"`, because the gate cannot tell whether the expansion lands as a value or as a flag.
- The one-word `--api-url=` is local only in a call the shell model reads in full (`backendLocal` and `oneWordTrusted` in `hooks/pre-bash-zensu-gate.sh`). The shell-model and PowerShell readings are judged on their words as the CLI receives them, quote characters included, and only the token scan's raw words are unquoted; the readings `dynamicReadings` derives never relax. The command must hold no `$` or backtick, because an expansion can rewrite the call (a function that forwards `"$@"`, an ANSI-C or locale string that spells the name) and the walker visits a substitution in a shell-read heredoc twice; no brace, because the walker expands only comma groups and stops at `MAX_BRACE_WORDS`; no carriage return, because the walker joins a backslash before CR LF as a line continuation and bash does not; no glob character; no `xargs`, which appends words from its input, and no `watch`, which re-parses its words through `sh -c`; on Windows no backslash, which the parse turns into `/` there; and no word built at run time in another way, such as a process substitution or an empty PowerShell argument or splat (`read` in `backendLocal`). Last, the walker must find as many `zensu` calls as `plain` holds `zensu` words in any letter case (the count is built from `NAMED.source`), so an escaped, quoted or uppercase name it finds cannot offset a call only the token scan sees. A local call that misses one stays denied, also beside a local `ZENSU_API_URL`, such as one with any `$`, a `?` or brace in a title, a JSON argument, a Windows path, `zensu` in any letter case in a title, an `echo` argument or a path such as `~/src/Zensu`, or `xargs` or `watch` in a title.
- The token scan reads raw words with their quotes, so a quoted noun or verb is judged only by the shell-model reading.
- The CLI name counts in any letter case, with the Unicode fold, and with quotes, backslashes, the `$` of an ANSI-C or locale string and line continuations removed, but not when it is assembled from variables or from an empty command substitution (`zen$()su`, an empty backtick pair) or spelled with ANSI-C numeric escapes (`$'\x7a'ensu`, which the walker decodes as `x7aensu`). The text readings also read more than the shell does, each a false positive in the safe direction: an escaped `\$` in front of a quote counts as an ANSI-C string (`zen\$''su`, which the shell runs as `zen$su`), a backslash or line continuation inside single quotes or an ANSI-C string is dropped although the shell keeps it (`'z\ensu'`, `$'zen\` and a line break before `su'`), and the fold upcases before it lowercases, so a dotless `ı` reads as `i`, as NTFS reads it and APFS does not. An ANSI-C string around a Windows path (`$'C:\…\zensu.exe'`) is not seen, because the walker drops the backslash of an escape bash does not know. When the module cannot load, the token scan misses a Windows path written with backslashes. A line continuation inside an inline `+=` assignment in front of the call (`ZENSU_API_URL\` and a line break before `+=…`) hides the call: the walker reads the joined word as the command, and the token scan reads no `+=` prefix. Also unseen, as before: a glob (`/opt/homebrew/bin/zens?`), a brace sequence (`{z..z}ensu`), a parameter default (`${X:-zensu}`), zsh's `=zensu`, a `zensu.cmd` or `zensu.bat` shim named with its extension, and a call that `trap` runs or `hash -p` binds to another name.
- The extra readings of an expanded word assume it holds flags and their values. An expansion that supplies the noun or the verb itself (`zensu features "$VERB"`) stays unjudged.
- The classification follows zensu-cli v0.10.0. A verb a later release adds stays unmapped, and passes, until the map learns it.

**Version: `minor`.** The gate now denies the work, plan, mocks and journeys-step mutations, the flag-value, empty-word and expanded-word spellings that hid a mutation, and a human decision or work-order verb inside a window that declares it, which changes the capability set of every session a newer installation would serve (`.claude/rules/runtime-lineage.md`). It also denies less: three reads and the `meta scaffold-agent` stub now pass. The backend reading of `backendLocal` is `minor` for the same reason: it denies a remote occurrence after a local one, an occurrence that may be another word's value, a remote one-word flag over a local `ZENSU_API_URL`, an empty inline assignment over a local hook environment, an inline `+=`, the hook's local value in a command that names the variable, a value whose host a URL parser reads as remote or that the shell completes at run time before its host ends, a PowerShell flag the analyzer cannot read, and on Windows an escaped `\--api-url` or `\--`, all of which the released gate let through; it reads `[::1]` as local, which the released gate never did. Reading the CLI name in any letter case and spelling is `minor` too: the released gate let `ZENSU`, `Zensu.exe` and `z\ensu` through ungated, and it let a command through whose parse failed, which the gate now denies.
